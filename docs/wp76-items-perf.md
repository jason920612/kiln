# wp76:大量物品實體的效能(對照原版 26.3)

分支 `wp76-items-perf`(從 main `59b41a28` 開出,只推到 `vm`)。

起點:wp74 的殺怪場景(掉落物不清)在約 4770 個物品實體時 Kiln 每 tick 約 30 ms、原版約 8 ms,清掉物品後 2 ms;
點名的熱點是 `EntityBox` 收集、`speculate`、`of_entity`。物品實體在真實伺服器上很常堆積(怪物農場溢出、TNT 坑、
水道物品流、收集區),所以這是真實差距,不是合成的。規則照舊:玩家照原版一樣 tick、沒有同步卡頓、整體 MSPT < 5 ms,
真實情境下至少和原版一樣快;行為逐位元不變(合併、撿拾、漏斗吸取時機、靜止物品的 motion 相位、state hash、封包)。

做法照馬斯克五步:先問每一塊每物品的工作是否必要、是否每 tick 都要(以原版自己的排程為準),能刪就刪,再簡化,最後才加速。
建置、測試、量測都只在 VM(12 vCPU、10 GB)上;開發期間 VM 和 wp77 共用,所以開發中的比較是交錯 A/B,
報告的數字見最後「數字」一節(量測時 VM 的狀態寫在那裡)。

## 一開始就發現的事

* **wp74 的「原版 8 ms」在相同的物品組合下重現不出來。** 同樣的物品放在同樣的地方,原版**比 Kiln 慢很多**(改之前):
  pile5000 原版 288 ms / Kiln 27.8 ms、hut5000 253 / 17.4、hopper5000 302 / 17.9、scatter5000 40.3 / 20.2。原版的
  `ItemEntity.tick` 每 tick 呼叫 `noCollision`,而 `getEntityCollisions` 會把物品所在區段裡**每一個**實體的盒子都測一次,
  密集時是每 tick N²;Kiln 沒有這一項(物品不撞物品)。wp74 的 4770 個物品不是原版也有的狀態:見下一點。
* **生怪數不一樣(沒修,記下來)。** `mobfarm8` 在 2008,2008(海上、夜晚、創造模式玩家):原版每回合殺掉約 50 隻,**普查完全沒有怪物**
  (只有蝙蝠、魚、魷魚、村莊的動物);Kiln 每回合約 125 隻,普查裡殭屍/骷髏/苦力怕/蜘蛛各 10–30 隻(怪物上限)。
  物品在原版累積到約 290、Kiln 約 380。wp74 的 4770 個物品很可能就是 Kiln 這邊多生出來的怪物掉的。原因沒查(不在這包的範圍,
  而且要先排除 bot 在原版的狀態),要另開一包用固定的黑暗盒子比對兩邊的 `NaturalSpawner`。
* **TNT 坑的掉落數不一樣(修了)。** 同樣 405 個 TNT:Kiln 留下 1033 個物品實體、原版約 300。原版的
  `ServerExplosion.interactWithBlocks` 先把一次爆炸所有方塊的掉落用 `addOrAppendStack` 收集(`StackCollector.tryMerge` 合到最多
  **16** 個一疊),最後才 `popResource`;Kiln 每個方塊各自掉。見「修改」1。
* **kiln-bot 預設視野 2,Kiln 只載入玩家客戶端視野內的區塊**;原版依伺服器的視野/模擬距離載入並模擬,和客戶端要的視野無關。
  所以先前用 kiln-bot 的比較裡 Kiln 模擬的範圍比原版小。這包的基準一律讓 bot 用視野 10(和真實客戶端常見的設定一樣)。
  載入語意的差異本身沒有改,列在「剩下的」。

## 時間花在哪裡(改之前)

開發中量的(VM 共用,交錯 A/B)。scatter5000(Kiln 改之前 11.5 ms/tick,原版 40 ms)的牆鐘分解,`KILN_PHASE_DETAIL`:

| 部分 | ms/tick | 說明 |
| --- | --- | --- |
| 實體清單 `e.list` | 7.1 | 推測視窗(平行)3.2 + 推測結果提交(序列)3.2 |
| 選擇器 `kill @e[type=!player,type=!item]` | 3.3 | 每次選擇器都替**每個**實體做一個 `PlayerRef`:UUID 字串、隊伍查詢、顯示名稱 `Text`(物品的 `hover_name` 會 `format!`)、把 NBT `extra` 整個複製去讀 `Tags` |
| `EntityBox` 收集 | 0.7–0.8 ×(每 tick 3–4 次) | 方塊相、實體相、方塊實體相(活塞/蓋子有時再兩次)各自把所有實體做成盒子,每個 ~200 bytes,還檢查掛畫、坐墊、船、潛影貝、快樂惡魂…… |
| `e.block_entities` | 0.8–0.95 | 其中一次 `EntityBox` 收集 + 漏斗的物品清單 |
| 追蹤 `mv.track` | 0.8–0.9 | |
| 傳送門候選(在 `light` 子階段) | 0.5 | 每 tick 每個實體查一次所在區段有沒有傳送門方塊(序列) |
| 撿拾 `ent.after` | 0.35 | 每 tick 每個實體解參考、算盒子,即使附近沒有能撿東西的玩家 |
| 壓力板 / post_touch / 索引 | 0.2 / 0.2 / 0.2 | |

整個行程的 CPU(`perf`,frame pointer):物品的 tick 42%(其中 `do_move` 11%、`apply_effects_from_blocks` 8.7%、兩次流體互動 15%、
`no_collision` 4.9%),推測時複製整個實體(1616 bytes)與配置/釋放約 20%(`Vec<Movement>` 每 tick 重新配置 2.1%、`VecDeque` 的 push、
流體 tracker 的 `Vec`)。

其他場景各自的大頭:

* **pile5000 / farm / reload(密集):** 推測一直暫停(`spec.off_listening`:區域裡有天然的伏聆振測器,深暗之域在地下很常見)或
  因為村民(`spec.off_serial`)整個區域都序列,`e.list` 22.6 ms;推測開著時,讀了別的物品的合併掃描一定作廢、改在原位重跑,
  每個要 36–50 µs:`note_touched` 用線性搜尋去重(合併時對上千個候選 `entity_mut`,O(k²)),每個候選兩次二分搜尋 + 解參考,
  不會合併的候選也呼叫 `entity_mut`(推測中還會為每個複製一份覆蓋層),`is_mergable` 每次都對物品預設元件做二分搜尋找 `max_stack_size`。
* **hopper5000:** 漏斗的 `items_in` 對每個漏斗把**所有**物品掃一遍(256 個漏斗 × 5000 = 每 tick 128 萬次盒子測試),`e.block_entities` 8.5 ms。
* **hut / 靜止的物品:** 推測的複製 + 配置 + 釋放約是物品 tick 本身的 60%;提交時對每個保留的回合解參考舊的和新的實體兩次(快取失誤)。
* **危害矩陣/熔岩:** 熔岩流動時流體 tick 每改一個方塊就同步傳播一次光照(熔岩亮度 15),佔流體 tick 的 80%;原版的光照引擎是非同步的。
  wp74 那一個 1.6 s 的 tick 在重現裡是場景開頭的 `forceload add`(生成 chunk;wp73 量過原版的 forceload 也卡 3–6 s),不是 `/fill` 或 `/summon`。

## 修改(依五步)

### 刪掉不必要的工作

1. **爆炸掉落照原版合併**(行為修正):`Event::BlockExploded`/`Effect::ExplosionDrop` 帶一個爆炸鍵,`blocks::finish` 把同一次爆炸
   連續的方塊掉落收進收集器(每疊最多 16,`are_mergable` + `merge_stacks(.., 16)`,位置是第一個方塊的),爆炸的方塊結束才 `pop_resource`。
   不衰減的爆炸(TNT)也走這條路。新測試 `explosion_drops_gather_into_stacks_of_sixteen`(5×5×5 泥土裡的 TNT:每疊 ≤ 16,只有一疊不滿)。
   TNT 坑:1033 → 264–283 個物品(原版 301–313),MSPT 4.4 → 1.6 ms(原版 7.2)。
2. **選擇器不再替每個實體做完整的 `PlayerRef`**:名稱(UUID 字串)與顯示名稱改成問的時候才做(`Named`/`Display`),隊伍只在記分板有人入隊時才查,
   `Tags` 直接讀欄位不複製;`SelectorWorld::entities_of` 讓 `type=`/`type=!`/`type=#` 與 `dx/dy/dz` 範圍在做 `PlayerRef` 之前就篩掉。
   scatter5000+killer 的選擇器 3.3 → 0.18 ms/tick。
3. **撿拾只看能撿東西的玩家附近**:先用外層位置篩(±4 格,遠大於盒子),沒有這種玩家就直接回;投擲者查詢只在真的有候選時才做。0.29 → 0.07 ms。
4. **每 tick 的全實體掃描跳過物品**:`update_data_before_sync`(只有生物有資料)與 post_touch(只有史萊姆類)先看類型。0.17 → 0.06 ms。
5. **漏斗依方塊欄找上面的物品**(`EntityItems.columns`):查詢只看重疊的欄,結果照原順序排序去重——和全掃完全一樣。hopper5000 `e.block_entities` 8.5 → 4.4 ms。
   (每 tick 對沒放進去的物品送 SetEntityData 是原版行為:`ItemEntity.setItem` 給的是新的 copy,`SynchedEntityData.set` 用 `ObjectUtils.notEqual`,
   `ItemStack` 沒覆寫 `equals`,所以一定標髒。保留。)
6. **推測不再整區關閉**:
   * 有振動監聽者(伏聆振測器等)時照樣推測:`SpecLevel` 遇到遊戲事件、振動、催發體都會 abort(改在原位跑),監聽者的狀態推測時從不讀。
   * 有村民或銅傀儡時照樣推測:這兩種**自己永遠在原位跑**;推測讀興趣點(`poi_in_range`/`poi_type`/`village_centers_near`/`sections_to_village`)
     會記在 log 裡,`SimLevel` 數興趣點的取得/釋放(`poi_writes`),有變就作廢;容器只有銅傀儡(和漏斗礦車)讀。
     其他 SERIAL 類型(sulfur cube、監守者、悅靈、苦力根、漏斗礦車、閃電、龍、終界水晶、凋零怪)仍然讓整區序列。
   * 新測試 `spec_villages`:村莊(床、工作方塊、鐘、6 個村民、鐵傀儡、銅傀儡)+ 伏聆振測器 + 240 個會/不會合併的物品,
     4 和 7 個 worker(含 chaos)每 tick 的 state hash 與封包串流都要和 1 個 worker(不推測)一樣,而且推測確實有保留(`SPEC_KEPT` > 0)。
7. **合併搜尋照原版的結構**:`EntityFilter::MergeableItem`(原版 `getEntitiesOfClass(ItemEntity, box, isMergable)`);迴圈裡先用 `entity()` 看
   會不會合併(`merges_with`),會才 `entity_mut`——不會合併的不再被當成「改過」(推測中也不再為它複製覆蓋層)。推測路徑仍然把區域內每個物品都讀一次並記錄(有效性要靠它)。
8. **流體 tick 的光照延到流體 tick 結束一次算**(`out.unlit` + `relight`,wp70 的多來源一次收斂,結果和逐一更新相同)。
   原版的光照引擎在別的執行緒、下一個 tick 之後才生效,所以流體 tick 中讀光照(例如蘑菇的 `canSurvive`)在原版本來就讀到舊值;改後在隨機 tick 之前就已經是新的。

### 簡化

9. `EntityBox`:物品走快速路徑(不是生物、不是掛畫/坐墊/船),`wear` 與 `player_source` 改成 Box(一個盒子 ~200 → 更小),先 `reserve`。
10. 推測提交:有效的推測不再呼叫 `carried()`(推測時就沒有載具,之後也沒人改過它);`shape()` 不再二分搜尋(索引已知);
    保留的回合帶著工作執行緒算好的前後形狀與同步欄位(`Synced`),提交時不再碰實體本體(兩次快取失誤);`settle` 的 cell 沒變就不查;
    每回合的計時只在 `KILN_PHASE_DETAIL` 時才做。
11. 原位回合記錄 `touched` 改用集合去重(`Touched`)。
12. `movement_this_tick`/`final_movements_this_tick` 改成 `SmallVec<[Movement; 2]>`,流體 tracker 改成 `SmallVec<[Tracker; 2]>`:推測複製時不再配置。
13. `max_stack_size`:沒有 patch 時查每個物品預設值的表(`defaults::default_max_stack_size`)。

### 加速

14. 傳送門候選分成 512 個一組在 tick 池上平行算。0.49 → 0.21 ms。
15. 區域搜尋用外層位置略過明顯在區域外的物品實體(物品的盒子是位置加固定的 0.25,而外層位置在實體相期間和狀態裡的位置逐位元相同:
    沒有任何回合會改另一個實體的位置,只改速度;乘客在自己的回合被定位;邊距取物品大小的兩倍)。`KILN_CHECK_PREFILTER=1` 會對每個被略過的物品
    檢查它的盒子真的不相交(最後的工作區測試開著它跑,真實場景也開著跑了一輪,沒有任何一次不符)。

沒做的(量過或想過):推測時只複製物品需要的部分(要改 `kiln-entity` 的 tick 介面);把 Entity 縮小(1616 bytes,`InsideCollector` 的 10 個 Vec 佔 240);
光照移出 tick 執行緒(原版是這樣做的,但這是架構級的改動,見「剩下的」)。

## 剩下的

* **5 ms 的目標在 5000 個物品時沒有達到**(8–14 ms;原版 30–290 ms)。剩下的大頭:推測時複製整個實體(1616 bytes)與釋放(可以只複製物品
  需要的部分,但要改 `kiln-entity` 的 tick 介面)、推測提交仍是序列、密集堆積裡每次合併掃描要看整個區段(原版也是,而且原版每 tick 還多一次 N² 的
  `noCollision`)、追蹤 0.7–0.8 ms、兩次 `EntityBox` 收集 0.4 ms。
* **光照在 tick 執行緒上**:熔岩擴張時的最差 tick 7–8 ms(原版 3–4 ms,原版的光照引擎在別的執行緒)。這包只把流體 tick 的光照批次化;
  真正的解法是非同步光照(wp70 也記過)。
* **怪物生成數和原版不同**(上面「一開始就發現的事」):原版在海上夜晚完全不生怪物,Kiln 生到上限。要另開一包比對 `NaturalSpawner`(可能是
  地下含水層/洞穴、或生怪位置的判斷)。
* **區塊載入依客戶端視野**(原版依伺服器的視野/模擬距離):客戶端視野小於伺服器時,Kiln 模擬的範圍比原版小。
* 有村民/監聽者的區域現在也推測,怪物多的區域推測常作廢,多用約 0.2 核 CPU(MSPT 不變)。
* 仍讓整個區域序列的 SERIAL 類型:sulfur cube、監守者、悅靈、苦力根、漏斗礦車、閃電、龍、終界水晶、凋零怪(悅靈與漏斗礦車和物品有關,
  需要先證明它們在原位改的東西推測都記得到)。
