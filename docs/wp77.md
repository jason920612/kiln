# wp77:關掉 wp74、wp75 留下的十個差異(屬性與 Brain 存檔、生怪上限、下界屋頂金農場、釣魚、村民補貨與折扣、貓晨間禮物與狐狸、傷害事件順序、被栓繩拉的 NoAI 牛、command_diff 的偶發差異)

分支 `wp77-gaps`(從 main `59b41a28` 開出)。做法承襲 wp72~wp75 的教訓:**比較的兩邊必須是同一個世界**(同種子、同方塊、同時間、同 gamerule)、
**位元精確的向量優先於統計**、樣本不夠不下結論、`@e` 不帶座標會跨維度所以每回合清乾淨。所有建置與測試只在 VM(`~/kt wp77-gaps …`、`CARGO_BUILD_JOBS=3~4`),
Kiln 25599、vanilla 25596;Mojang 的資料留在 `work/`,不進 repo。新向量在 `work/wp77/`(`saved.jsonl`、`brt.jsonl`、`fishing.jsonl`、`villagers.jsonl`),
沒有改任何共用檔(`work/m6-mobs2/vectors.jsonl` 等不動)。

方法上的收穫:**把兩邊每個生怪決定都記下來,而不是只比最後殺到幾隻**。第 4 項的差異(Kiln 比 vanilla 多 1.3~2 倍)沿著「晶片嘗試數 → 起點數 → 挑選 → 有效列」逐層比,
每一層都相同,最後才在「起點的高度」這一層露出來。

## 1. 實體 NBT `attributes`(生物與玩家)

**vanilla**(`AttributeMap.pack`):存**所有已建立實例**(`getInstance` 建立;單純讀 `getValue` 不建立);每個實例寫 `base`,`modifiers` 只存**永久**修飾(效果的 `minecraft:effect.*`、
`/attribute … modifier add` 的永久修飾);裝備、疾跑、幼體、`attacking` 這類是暫時修飾,不存。
**Kiln 原本**:存全部屬性清單、也存暫時修飾。
**修正**:`AttributeInstance.created` 旗標,存檔只寫 `created` 的實例;暫時修飾(`Modifier.transient`,`set_transient_modifier`)不存;載入對沒有實例的屬性不建立;
玩家比照(`combat::attributes_nbt`、`saved_attributes`:幾種屬性靠效果、裝備、指令碰過才有實例)。順手:`AgeableMob.setAge` 跨過 0 會呼叫 `ageBoundaryReached`(山羊、豬布林的攻擊傷害實例),
載入的山羊與豬布林只有在幼體時才讀 `IsBaby`;盔甲架的 `speed_made`。
**證據**:`saved_parity.rs` 對 `saved.jsonl` 的 **7,604 筆(每種活實體 `/summon` 後與五個 tick 後)全部與 vanilla 相同、0 筆不同**(隨機裝備的怪物裝備屬性、隨機初值的屬性基底、已死亡的、
年齡不同的案例是有明列的容忍,見測試開頭);`player_attributes.rs`(玩家登入、效果、指令);`kiln-entity` 單元測試 `an_attribute_has_an_instance_once_it_is_asked_for`。
拿掉修正(`.filter(|i| i.created)`)`saved_parity` 失敗。

## 2. `Brain.memories`(存檔與 `/data get`)

**vanilla**:`LivingEntity.readAdditionalSaveData` 讀到 `Brain` 標籤就用它重做腦(`makeBrain(packed)`),**所有活實體都讀**(沒有腦的類型記憶表是空的,存出來也是空的);
只有有 codec 的記憶存(52 種);`Unit` 記憶的 codec 是 map codec,**值必須是複合標籤**,別的型別整筆丟掉;銅傀儡建構時放的 `transport_items_cooldown_ticks` 被存檔的腦取代而消失。
**Kiln 原本**:只有幾種腦類型讀、`Unit` 吃任何值、銅傀儡的冷卻留著。
**修正**:`brain/persist.rs`(`Unit` 必須是複合)、`mob/persist.rs`(每個活實體都讀 `Brain`、`Kind::brain_replaced`)、`copper_golem.rs`。
**證據**:`brain_parity.rs` 對 `brt.jsonl` **5,028 筆全部相同**(每種活實體放全部可序列化記憶,有腦的類型各記憶單放、有無 `ttl`、無效值、未知記憶,一與三個 tick 後存出來的記憶、值、剩餘時間)。

## 3. 自然生怪的上限計數

**vanilla**:`createState` 數**所有載入的實體**(類別不是 MISC、排除持久與自訂持久的生物),不管在不在會 tick 的區塊;全域上限
`canSpawnForCategoryGlobal`(`count < max × spawnableChunkCount / 289`)每個 tick 只決定一次(`getFilteredSpawningCategories`);`spawnableChunkCount` = 追蹤中玩家 8 區塊內的區塊數(旁觀者只有 `spectators_generate_chunks` 時);
`natural_mob_spawns` 是全解析度生物群系屬性(要用 `BiomeManager.getBiome` 的雜訊位移查詢,不是儲存的 4×4×4 格);狼的 `getMaxSpawnClusterSize` 是 8。
**Kiln 原本**:只數玩家 8 區塊方形內的生物,所以 wp74 看到的「重啟後 100 隻怪佔滿上限」vanilla 不生、Kiln 照生;群系用儲存格;狼 4。
**修正**:`spawner::SpawnTotals`(整個維度的生物與區塊數,在區域跑之前加總;**單一區域的維度也一樣在 tick 開頭加總**,否則「一個區域」與「每組一個區域」數的時間點不同——見下面「determinism」)、
`spawn_biome`(`weather::biome_at` 的位移查詢)、`persistent_for_counts`(水生與末影人等「需要自訂持久」的類型)、狼 8。
**測試**:`spawn_cap.rs`(遠處載入的區塊裡的動物佔滿上限、Kiln 不再生)、`kiln-entity/tests/spawn_cluster.rs`(vanilla 各類別的群大小:預設 4、狼 8、馬 6、魚 8、鮭魚 5、幽靈 1…)。

## 4. 下界屋頂金農場、終界外島末影人農場、傳送門豬人

**工具**:兩邊都記每個生怪決定(vanilla 用 java agent,Kiln 用 `spawner::stats`,鍵相同):晶片嘗試、起點(`start`)、挑選(`getRandomSpawnMobAt`)、`isValidSpawnPostitionForType` 的每一列(附上它屬於哪個起點)、
`isValidPositionForMob`、全域上限、類別清單。**兩邊的世界相同**(種子 77、雜訊世界、同一個平台、同時間、同 gamerule、模擬距離 8),鎖步:每回合跑 N tick,數方塊盒子裡的生物,殺光,盒外清掉。

**下界屋頂(平台 15×15 在 y=128)**:一輪 rounds=40×600 tick 的僵屍豬人:Kiln 119、vanilla 56(第一次發現時)。逐層比:晶片嘗試數相同,起點數相同,挑選相同,有效性相同(只有 y=129 是有效位置)——
**起點的高度分布不同**:Kiln 在整個屋頂的每一欄都有 1/130 的起點在 y=129(≈730 次,與 y≤128 一樣多),vanilla 在平台以外的欄位**從不**在 y=129(≈33 次,只有平台欄位)。
**根因**:`NaturalSpawner.getRandomPosWithin` 的上限是 `chunk.getHeight(WORLD_SURFACE, x, z) + 1`,而 `ChunkAccess.getHeight` 回傳的是**最上面方塊的 y**(`heightmap.getFirstAvailable − 1`),所以上限是「欄位上方第一個空位」(基岩屋頂到 y=127 → 128);
Kiln 的 `column_height` 本來就回傳「第一個空位」,又加了一次 1(→ 129)。平台外 y=129 的起點成員隨機走到平台上(y 不變、x/z 隨機走),那裡的 y=129 是有效位置,於是**多出約 1.3~2 倍的豬人**。這個偏差在整個世界的自然生怪都在(起點比該有的高一格),只是屋頂平台把它放大成可見的數字。
**修正**:`spawner::start_top`(= `column_height`)。**證據**:修正前 `y=129` 起點在屋頂欄位 K 733 / V 33(單一輪),修正後 K 34 / V 44;`true` 列「起點在盒外」K 85 / V 0 → 兩邊都是 0;
`a_start_reaches_no_higher_than_the_first_free_block_above_the_column`(基岩到 127 → 128;平台在 128 → 129;空欄位 → 世界底)。修正後一輪(60 輪×600 tick):K 僵屍豬人 45 / V 82、豬人 16 / 10(單輪的 χ² 受 pack 影響很大,起點每個 y=129 的 `true` 列 K 3.21 / V 3.50,逐起點的分布相同);
沒有再找到系統性的差異(見「剩下」)。

**終界外島末影人農場**(平台 15×15 在 y=40):40 輪×600 tick,**K 56 / V 56**(挑選 79 / 86、有效列 `true` 81 / 90,逐列的 χ² 都小)。

**主世界傳送門方塊的殭屍豬人**:**Kiln 原本沒有**(`NetherPortalBlock.randomTick` 沒接)。vanilla:`isSpawningMonsters`、難度不是和平、維度屬性 `nether_portal_spawns_piglin`(主世界)、
`nextInt(2000) < 難度 id`、玩家在生怪範圍內(離區塊中心 128 格,不含旁觀者)、沿傳送門柱往下到第一個非傳送門方塊、那個方塊對殭屍豬人 `isValidSpawn`(玩家以外的一般規則,岩漿塊因為免疫火所以也可以)、
在它上面生一隻(`EntitySpawnReason.STRUCTURE`)並 `setPortalCooldown()`(300 tick;`Entity.portal_cooldown` 新欄位,存檔 `PortalCooldown` 本來是原樣帶過)。
**修正**:`behaviour/portal.rs::random_tick`、`Level::portal_piglins_possible`/`portal_piglin_spot`、`Effect::PortalPiglin`。**證據**:`portal` 場景(40 輪×200 tick,`random_tick_speed 4096`,6 個傳送門方塊):**K 40 / V 48**(期望 48);`portal_piglins.rs`。

**殺怪指令方塊在下界與終界在兩邊都沒動作**:不是 Kiln 或 vanilla 的錯。主控台的指令來源在主世界,`@e[x=..,dx=..]` 這種有體積的選擇器**只找來源所在的維度**(`@e` 不帶座標才跨維度);
所以 `kill @e[x=…]` 在下界與終界是 0。要殺要用 `execute in minecraft:the_nether run kill @e[…]`(`farm77.py` 就這樣做,兩邊殺到的數字才有意義)。

## 5. 釣魚

`FishingVectors`(150 個浮標案例,每 tick 13 個值,共 778,453 個值)對 `fishing_parity.rs`:
- **找到並修正的錯**:浮標在**流動的水**(`water[level=1..7]`)裡不浮(Kiln 只認水源 `FluidKind::Water`,vanilla 是 `fluidState.is(FluidTags.WATER)`,流水也算)——修正後 **8 個不同的案例變成 5 個**。
- **咬鉤時浮標往下沉**(`onSyncedDataUpdated(DATA_BITING)` 在伺服器端也執行,動量 `-0.4 × (0.6~1.0 同步亂數)`):Kiln 原本沒有。
- 開放水域(5×4×5)、Lure 的等待時間(`100×level`)、幸運(鉤子的 luck + 玩家運氣)、`syncronizedRandom`(每 tick 以 UUID 低位 ^ 遊戲時間重種)、戰利品池:在這 150 個案例的每 tick 狀態裡全部相同;
  `fishing::rod_value` 對每一組 Luck of the Sea × Lure 與 vanilla 讀的 `FishingLuckBonus`/`FishingTimeReduction` 相同(16 組)。
- **還剩 5 個案例不同**(`fishing_20/32/50/68/116`):`fishing_50` 看得最清楚——浮標靜止在 `x=8.125`(盒子的 `minX` 剛好是 8.0)貼著隔壁欄位的冰與活板門,vanilla 的那一步垂直速度變成 0,
  Kiln 沒有:是方塊形狀碰撞的邊緣處理(和釣魚邏輯本身無關,計時與亂數抽取一致),**沒有調查**;`fishing_parity.rs` 把這五個明列為已知差異,多出來的差異會失敗。
  原本的「開放水域 5/125 對 8/124」是 wp74 在統計上看到的差異;這個向量比對在 150 個案例裡 `open water` 欄每 tick 一致,所以那個差異不是 `open water` 判斷的錯,
  更可能是 wp74 的世界不同(浮標在流動的水裡不判斷為水,與上面修正的錯同方向)。

## 6. 村民補貨與折扣

400 個案例 5,580 步,`villager_parity.rs`:**0 個不同**。涵蓋:`GossipContainer`(`add`、`decay`、`transferFrom` 含 `selectGossipsForTransfer` 的加權挑選與二分搜尋、聲望加總)、
`MerchantOffer`(`updateDemand`、`resetUses`、`increaseUses`、特價疊加)、`updateSpecialPrices`(聲望 × `priceMultiplier`、Hero of the Village 的 `0.3 + 0.0625 × amplifier` 折扣,疊加在聲望之上)、
`shouldRestock`(`lastRestockGameTime` 12000 重設、第二次補貨 2400 之後、`restocksToday`、日換日時間)與 `restock`(需求補算、使用次數歸零)的時間腳本。
**修正的只有一個**:`Gossips::transfer_picked` 改成與 `Arrays.binarySearch` 一樣的二分(同值時挑選的位置與 Rust 的 `binary_search` 不同)——**沒有差異,因為向量的八卦分數沒有相同值**,但留著比較安全。
**vanilla 自己不可重現的一處**:`transferFrom` 挑選順序取決於 `unpack()` 的走訪,`GossipContainer.gossips` 是 `HashMap<UUID,…>`,每個玩家內部是以**列舉的身分雜湊**為鍵的 `Object2IntOpenHashMap`
(`Object.hashCode`,每次 JVM 啟動都不同),所以逐位元比對要用向量記下的 `unpack()` 順序(`VillagerVectors` 記 `order`)。
**治療殭屍村民的八卦**不在向量裡(向量從 `GossipContainer` 起),改用位元碼核對:`Villager.onReputationEventFrom` 的 `ZOMBIE_VILLAGER_CURED` 是主要正面 +20 與次要正面 +25、`TRADE` 交易 +2、`VILLAGER_HURT` 次要負面 +25、`VILLAGER_KILLED` 主要負面 +25,與 Kiln 的 `Gossips::on_event` 相同(單元測試 `cure_reputation_and_caps`:聲望 125、衰減後 124);`HeroOfTheVillage` 對價格的折扣在 `special` 向量裡。
**工具的兩個錯**(都是 harness 的,不是 Kiln 的):報價案例的 `setup` 在跑完步驟之後才記(重放從最終狀態開始);`EntityType.VILLAGER` 在 26.3 是 `EntityTypes.VILLAGER`。

  - 「鐵傀儡不回村、不保衛村」「堆肥不模擬」→ **已有**(`iron_golem.rs` 的 `DefendVillageTarget`/`MoveBackToVillage`、農夫堆肥);
  - 「交易表擲法與原版不同」→ **設計取捨,不改**:vanilla 的交易表用世界共用的亂數序列(`minecraft:trade_set/<職業>/level_<n>`,存進世界),擲的順序取決於全世界村民升級的先後;
    Kiln 的區域平行模型下這個順序不存在,所以以世界種子、tick 與村民 id 為種子擲(分布相同,逐位元不同)。

## 8. 傷害事件對「直接送出的 level event」的順序

**vanilla**:`LivingEntity.hurtServer` 在傷害落下時立刻廣播傷害事件(`broadcastDamageEvent`),之後才有 `ThrownSplashPotion.onHit` 的 level event 2002/2007。
**Kiln 原本**:玩家的傷害事件要等到該 tick 結尾的廣播才發出,而 level event 直接進出口佇列——旁觀者先收到 level event 才收到傷害事件。
**修正**:`Event::PlayerHurt { target }`(`hurt_player`、`thunder_hit_player` 與藥水的 `apply_instantaneous_effect` 對玩家都會推),`flush_player_damage` 在事件順序裡那個位置把傷害事件送給看得到的人。
**測試**:`player_sync.rs::the_damage_event_comes_before_a_level_event_sent_at_once`(傷害藥水水濺到生物與玩家:旁觀者先收到傷害事件再收到 level event)。

## 9. 被栓繩拉的 `NoAI` 牛的 `Motion`

**vanilla**:`Mob.isEffectiveAi()` = `LivingEntity.isEffectiveAi() && !isNoAi()`,`NoAI` 的生物不跑 `serverAiStep` 也不 `travel`,所以 `Leashable.elasticRangeLeashBehaviour` 加在動量上的值**沒有摩擦力**,
`Motion` 持續累加、位置不動。
**重查**:兩邊同一個世界(平台在 y=200、`NoAI` 牛離柵欄結 7.5 格;另一組是玩家握著栓繩),`tick freeze` + `tick step`,每 1 tick(結)與每 5 tick(玩家)抽樣 `data get entity … Motion`:
**結 40 個、玩家 40 個樣本(共 200 tick),Kiln 與 vanilla 逐位元相同**(`Motion` 的 x 累加到 3.39、玩家的一組收斂到 1.4143…、z 到 0.0)。wp75 看到的差異不能重現
(wp75 的比對是 `tick step` 速度不同造成的取樣時間差,或更早修正的東西);沒有 Kiln 的修改。
**測試**:`leashes.rs::a_noai_cow_pulled_by_a_lead_keeps_the_motion_vanilla_does`(vanilla 的前 14 個 `Motion` 值逐位元)。

## 10. `command_diff` 的偶發差異

**`data get entity Diff0 Health` 19 對 18**(wp75、wp77 開頭各見一次,緊接在 `damage Diff0 2` 之後):
- **沒有重現**。同一串指令(`gamerule natural_health_regeneration false` → `damage Diff0 2` → `damage … nonexistent` → `damage Nobody 1` → `data get entity … Health`)在兩個伺服器上用機器人 W0 重複 120 次,
  每次前面隨機停 0~100 ms,**K 與 V 都是 120 次 18.0**(`tools/wp77/flake10.py`);完整的 `command_diff` 本分支跑了 4 次(1956/1956、1954/1956、1956/1956,以及修改後的最終三次),健康值那一行從沒不同。
- 能想到的機制只有「受傷前的血量不是 20,或兩邊在受傷與讀值之間有一次自然回血」,兩者都取決於前面各節(`ride … dismount` 的落下、`gamemode survival @a` 之後機器人還在落地)與現實時間的相對位置,
  是**測試腳本的時機依賴,不是 Kiln 的不確定**(兩伺服器的 tick 與現實時間的對應不同:vanilla 全速,Kiln 每 tick 50 ms)。
- **處理**:讓這一行不再依賴時機——關掉自然回血後用 `instant_health` 補滿、等 1 秒(受傷冷卻過去)再 `damage`(`tools/command_diff.py`)。

**另一個偶發差異(這次找到原因)**:三次完整跑中有一次是 `fetchprofile name Other0` 兩個伺服器的「Failed to resolve profile」訊息一邊落在 5 秒窗口裡、一邊落在下一個指令。
原因:VM 連不上 session server,名稱或 id 的查詢在**兩邊都約 5.0 秒後**才失敗,而腳本的 `~ 5` 只等 5 秒——誰先誰後是丟硬幣。
**處理**:這一節的 `~ 5` 全部改成 `~ 8`。

## 附帶發現

- **determinism**:自然生怪起點上限修正後,`determinism.rs` 在 `KILN_DATAPACK` 下失敗(一個區域 vs 每組一個區域,第 4 個雜湊不同)。逐層查出來:兩邊的生怪位置完全相同,
  **只有兩隻快樂恐懼魔的 `vel` 不同**——`state_hash` 讀的是 `Entity` 記錄裡的 `vel` 副本,它只在實體 tick 或有人建一個圍繞它的關卡(`with_level` 的最後 `sync`)時才更新,
  而「建關卡」的範圍取決於區域怎麼切(單一區域的人用柵欄用栓繩就把全部實體 sync 一遍);實體本身的 `delta` 兩邊相同。修正:雜湊讀 vanilla 狀態的 `delta`(`phys.delta`)。
  同時單一區域的維度也在 tick 開頭加總生物數(第 3 項),所以「一個區域」與「多個區域」對上限的計數時間點一致。
- **`cat.rs` 的 `atan2`** 用了標準庫(`no_std_libm` 測試抓到),改成 `Mth.atan2`。
