## 2. 逐項

### 2.1 `/damage` 與擊退(項目 1)

vanilla 的順序:console/聊天指令(兩個 tick 之間)、tick function、排程方塊 tick(指令方塊)都在 `ServerEntity.sendChanges` 之前;玩家自己的 `travel`(`ServerGamePacketListenerImpl.tick → doTick`)在實體階段之後的連線階段。所以這些路徑造成的擊退,客戶端收到的是**原樣**的速度(水平 0.4、垂直 `min(0.4, -0.0784/2 + 0.4) = 0.3608`),而實體階段裡的打擊(殭屍打玩家)才是走過一步的(0.2184 / 0.2752,wp84 已對)。`Player.causeExtraKnockback`(玩家自己的衝刺擊退)是另一條:立刻送出受害玩家的速度再還原。

Kiln:`Player.sync_stepped`/`sync_held`/`sync_raw`(`players.rs encode_movement` 決定要不要走那一步;`region.rs` 在 `player_tick` 結尾記下已經走過),「tick 之外造成的打擊」`freeze_unstepped_hits()`。測試 `damage_knockback_wp87.rs`:`/damage` 指令、指令方塊的 `damage`、實體階段的打擊仍然要等那一步(三個)。`neg87.py unstepped`:拿掉就失敗。

### 2.2 seed 84 的世界生成(項目 2)

wp84 在兩個活伺服器上看到:沙漠金字塔正下方一座只有 Kiln 有的地下城,以及暖海遺跡裡 6 塊多出的可疑沙。步驟:

1. **vanilla 對 vanilla**:`tools/wp87/OrderVectors.java`(由 `make_order_vectors.py` 從 `tools/wp85/PackVectors.java` 產生)讓 vanilla 的類別用**指定的裝飾順序**(九個 chunk 類別的排名)生成同一批 chunk 並傾印。Kiln 取的「正規順序」是 `RANK = {0,1,2,7,6,3,8,5,4}`;另外兩種合法順序(反向 `8,7,6,5,4,3,2,1,0` 與另一種 `c`)。`wp87_order.rs::vanilla_itself_changes_with_the_decoration_order`:同一批 128 個 chunk、同一個 seed,vanilla 在三種順序之間就有 **29,938 個方塊**不同(第二種順序 115/128 個 chunk 有差、12,869 個方塊:花崗岩/閃長岩/安山岩的礦脈互換、海草與水…)。金字塔下方的地下城(-770,-36,156 一帶)在順序 c 是 `mossy_cobblestone` 的地方,正規順序是 `deepslate`——也就是**地下城本身是順序決定的**;vanilla 的順序由多執行緒的時序決定,Kiln 固定一種,不可能讓一個固定順序和「兩個」活的 vanilla 世界都相同,這個差異**不是 Kiln 的錯**。可疑沙:遺跡範圍內三種順序的 vanilla 都是 5 塊,Kiln 在正規順序下也是 5 塊——**順序解釋不了 wp84 看到的 6 塊多出來的沙**。
2. **Kiln 對 vanilla(同一順序)**:`wp87_order.rs::seed_84_around_the_pyramid_and_the_ruins_matches_vanilla_in_kilns_order`:同一批 chunk 方塊與結構 start NBT 逐項相同(0 個差異),但一開始 start 的 NBT 有差:海底遺跡與沉船的 piece 在 `postProcess` 時會改 `templatePosition` 與包圍盒(海底遺跡取 `OCEAN_FLOOR_WG` 的高度、沉船 `adjustPositionHeight`),vanilla 存檔存的是**放置後**的,Kiln 存的是放置前的。跨 chunk 的遺跡其餘部分是之後由鄰近 chunk 依**存下來的** start 繼續放的,所以存放置前位置會讓後放的部分用錯的高度——這是可疑沙(挖出來的沙層在遺跡底下)最可能的來源,但我沒有在兩個活伺服器上重現當時那 6 塊的數字,所以這一條是「找到並修了一個真的存檔差異,最可能就是它」,不是「已證明就是它」。修了(`ocean_ruin.rs`/`shipwreck.rs` 記下放置後位置,`bbox_now`/`save_extra` 用它)。`neg87.py ocean_ruin_save`。

### 2.4 自訂維度(項目 4)

**4a 時鐘與 timeline**:26.x 的時間不再只有一個白天時間。`world_clock` registry、`timeline` JSON(`clock`、`period_ticks`、`time_markers`、`tracks` 的關鍵影格/緩動/修飾)、維度類型的 `default_clock` 與 `timelines` tag。Kiln:`kiln-sim/src/timelines.rs`(新)取樣(`KeyframeTrackSampler` 的段落語意),`weather.rs`(`ClockSlot`:每個時鐘自己的 `total`、速率、暫停;`sky_darken_with`、`weather_layer`、`marker_move_in`),維度各看自己的時鐘:睡覺、天空亮度、`monsters_burn`、`creaking_active` 等屬性來自維度類型的 `timelines`;`/time of <clock> set|add|pause|resume|rate`、`/time set <marker>`、Set Time 封包帶全部時鐘(含自訂的)、存檔 `world_clocks.dat`(`kiln-storage` 的 `ClockSave`)。測試 `dp_clocks_wp87.rs`(4 個:時鐘自己跑、marker 與週期、維度跟著自己的時鐘、客戶端收到與重啟後保留),`neg87.py`:`clocks_run`、`markers`、`level_clock`、`clock_saved`。資料包 `tools/wp87/packs/kiln87_clock`。

**4b 平坦生成器**:`FlatLevelSource` 的行為(位元碼):`buildTerrain` 直接填各層(`null` 的跳過);`adjustGenerationSettings`:`lakes` 時 `LAKES` 步驟放熔岩湖(`createLakesList`),`features` 且不是全空氣(或是 `the_void`)時放群系的所有地物**除了** `UNDERGROUND_STRUCTURES`、`SURFACE_STRUCTURES`(`lakes` 時連群系的湖也不要);不透明以外的層改由 `FillLayerFeature` 在 `TOP_LAYER_MODIFICATION` 補;`structure_overrides` 是結構集的白名單(沒寫 = 全部);**`getMinY()` 是 0、`getGenDepth()` 是 384**(所以 `above_bottom`/`below_top` 的高度範圍從 0 起,不是 −64,地下礦脈在平坦世界裡大多不會長出來——這個是對照 vanilla 才看到的差異:一開始 Kiln 的礦脈多出十倍)、`getSeaLevel()` −63。Kiln:`Generator::for_flat`(層、固定群系、`gen_min_y = max(min_y, 0)`、`gen_height = min(height, 384)`、海平面 −63)、`Decorator::new_flat`(`FlatDecoration`)、`Structures::load_only`(`structure_overrides`,含 `#tag`)、`Worldgen::flat`,`kiln-sim` 的 `Made::FlatFull`(只在需要時走完整流水線,純層狀的世界還是用 `FlatChunks`);`mineshaft`、`stronghold`、`ruined_portal` 問的是 `chunkGenerator.getMinY()`(`GenCtx::generator_min_y`,平坦是 0)。

驗證:`tools/wp87/FlatVectors.java`(由 `make_flat_vectors.py` 從 `PackVectors.java` 產生,生成器換成 `FlatLevelSource`)讓 vanilla 載入 `tools/wp87/packs/kiln87_flat`(四個平坦維度)生成並傾印,`crates/kiln-worldgen/tests/wp87_flat.rs` 讓 Kiln 用同一疊根生成並比較:`features`(128 chunk)、`lakes`(200)、村莊白名單(1712,2 個 start)、不寫 `structure_overrides`(1416 chunk,**11 個結構 start**:礦坑等),**全部 0 個方塊差異、0 個 start 差異**。`dp_flat_wp87.rs`:執行中的伺服器裡平坦維度確實長出草、花、樹。`neg87.py`:`flat_depth`、`flat_structure_depth`、`flat_pipeline`、`flat_overrides`。

**沒做/限制**:不透明以外的層(水、雪層)在流水線路徑裡直接放進地形,不是 `FillLayerFeature`(結果相同,只是和樹等地物的先後順序理論上可能不同);jigsaw 結構問的最低高度在平坦世界用關卡的(vanilla 用 `heightAccessor`,未逐位元碼確認)。

### 2.5 鎖步比對(項目 5)

**5a 重錘**:`tools/wp87/MaceFall.java` 在行程內開 vanilla 伺服器,用 mock `ServerPlayer`(`EmbeddedChannel`)從不同高度落下(客戶端自己的物理,每刻一個位置封包)並在指定刻攻擊,涵蓋密度/突破/風爆;傾印傷害、受害者速度、重錘耐久、攻擊者剩餘的掉落距離與爆炸封包。`mace_fall_wp87.rs`:Kiln 收到同樣的封包(同一位置、同一刻)給出同樣的結果,**91 個情境、0 個不同**(曾有 11 個風爆速度的最後一位元差,原因是 harness 的起點座標在二進位下不精確,改成 Y0 = −63、FX = 1.25 後消失,不是 Kiln 的差異)。

**5b 凋零**:位元碼:`WitherBoss` 的側頭選目標是 `getNearbyEntities`(範圍 20、`TARGETING_CONDITIONS` 含視線)後 `random.nextInt(size)`,Kiln 的邏輯相同(`kinds/wither.rs`,`KILN_WITHER_TRACE` 可記錄每次選擇與候選數)。兩名玩家相距 10 格、凋零在中間:`wither_targets_wp87.rs`(400 次選擇,候選數恆為 2,Kiln 211/189,斷言每名玩家各占 40~60%);活伺服器並排 40 輪(`tools/wp87/farm87.py wither`):Kiln 與 vanilla 都兩個人都會被選到(vanilla 80 次 38/42,Kiln 80 次 53/27 和 211/189 都在隨機波動範圍內)。**沒有差異**。(第一次並排 Kiln 的兩名玩家被選到的是同一個位置,是 harness 的傳送沒到位,不是 Kiln:改成玻璃平台後分布公平。)

**5c 快樂恐魂牽拴繩**:`Leashable.checkElasticInteractions`:持有者 `supportQuadLeashAsHolder`(`HappyGhast`、`Ghast`)且被牽者 `supportQuadLeash`(船、`AbstractHorse` 含駱駝、嗅探獸;Llama 不是)時用 `SHARED_QUAD_ATTACHMENT_POINTS`(±0.5, 0.5, ±0.5)四點彈簧,力矩累加,縮放 0.25,否則單點。Kiln 的 `leash.rs` 原本一律單點;改成 `Holder { quad }` 與 `supports_quad_leash`。`tools/wp87/LeashQuad.java` 對 84 個設定呼叫 vanilla 的 `Leashable.tickLeash` 12 次;`leash_quad_wp87.rs` 讓 Kiln 的 `tick_leash` 在同樣設定下給出同樣的 delta、yaw、角動量。`neg87.py quad_leash`。

### 2.6 下界屋頂的 MONSTER(項目 6)

wp82 看到下界屋頂的殭屍豬人農場上,Kiln 每刻選 MONSTER 類別的次數比 vanilla 多 5~10%。鎖步並排(`tools/wp87/run87.sh nether`,種子 77、兩邊同樣 30 輪;agent 計數器 `chunkAttempt`、`pick`、`validPosition`、`validMob`、`spawned`):

| | Kiln(修正前) | vanilla |
|---|---|---|
| `validMob IN-BOX zombified_piglin -> true`(屋頂 y=134) | **0** | 48 |
| 同一位置 `-> false` | 57 | 2 |
| 殭屍豬人殺掉數(30 輪) | 0 | 數十 |

原因:Kiln 對**每個維度**都存天光(把下界當成開放的天空),所以下界屋頂(基岩之上)天光是 15,`isValidPositionForMob` 的光亮度檢查擋掉所有怪;vanilla 的下界(`has_skylight: false`)沒有天光層(`LevelLightEngine.skyEngine` 為 null),屋頂和屋頂下一樣暗。農場在 Kiln 沒產出,所以(固定上限的)`SpawnState` 一直沒填滿、一直在嘗試,多出的 5~10% 嘗試次數只是它的後果。修正:`blocks::sky_light_at`(沒有天光的維度回 0),所有讀天光的地方(`sky_light`、`raw_brightness`、實體/生怪的視圖、`can_see_sky`、進度條件的 `CellProbe`)都走它。修正後同一個 harness 兩邊:每次嘗試的 MONSTER 選擇 Kiln 1.131 / vanilla 1.126、生出 2381 / 2392、農場殺掉 29+2 / 27+3(修正前 Kiln 完全沒有殺掉)。測試 `nether_sky_wp87.rs`;`neg87.py nether_sky`。

## 3. 狀態雜湊與封包 golden

這個套件沒有重錄 `crowd_golden` 的封包摘要:改動只有(a) tick 之外的擊退封包不走那一步(只影響 `/damage`、指令方塊)、(b) 沒有天光維度的光亮度,(c) 生物附魔效果(沒有穿附魔裝備的生物不受影響),(d) 平坦維度的路徑;人群劇本的狀態雜湊在這些改動前後相同(`crowd_golden`/`determinism.rs` 綠)。
