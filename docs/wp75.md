## 1. 漏斗鏈的 ±1 延遲

**根因**:vanilla 的方塊實體 tick 順序是 `Level.blockEntityTickers` 這個串列的順序,也就是**建立的順序**(放置的順序;載入的區塊則依 `LevelChunk.blockEntities` 這個 `HashMap<BlockPos, BlockEntity>` 的走訪順序)。
Kiln 一直按座標順序 tick。一條漏斗鏈裡誰先 tick 決定一個 tick 內物品走幾格、冷卻的進位(`tryMoveInItem` 的 `k`)落在哪裡;原本的向量腳本剛好按座標順序放方塊,所以一直通過。

**修正**:`ContainerBe::order`(建立時的序號,跟著方塊實體走過區域合併與分裂,`/data` 重載保留舊序號);`Containers::ticking` 依序號排序;`chunk_loaded` 依 Java `HashMap` 的走訪順序(`java_hash_order`:`Vec3i.hashCode`、桶號、表容量 16 起每超過 3/4 加倍、同桶依放入順序)載入。

**證據**:160 條隨機漏斗鏈逐 tick 逐值(97,343 個值)與 vanilla 相同,其中 30 條有礦車(漏斗礦車/箱子礦車)、有比較器、有紅石鎖;把 tick 順序改回座標順序,**約 100 條失敗**(每種非座標順序的放置都失敗)。
`java_hash_order` 對 Java `HashMap`(用 vanilla 的 `BlockPos` 類別)產生的 5/13/30 個鍵的走訪順序逐項相同。
**測試**:`tests/hopper_order.rs`(兩個:先放上面/先放下面的漏斗疊,15 行逐 tick 的 vanilla 數字)、`container::tests::java_hash_map_order_of_block_positions`。

## 2. 靜止物品 `Motion` 的次毫米漂移

**結論(三個原因,都找到了)**:

1. 靜止的物品每四個 tick 才 `move` 一次,時機是 `(tickCount + id) % 4`。**id 不同,`Motion.y` 的鋸齒相位就不同**(位置不變)。Kiln 的 id 不可能和 vanilla 的絕對值相同,但**同一個 tick 內用指令生成的幾個實體,相對順序**應該一樣:Kiln 是「依座標排序」配發 id(為了讓區域拆分不影響 id),所以三個 `/summon` 的 id 順序和指令順序不同,相位就和 vanilla 不同。
   修正:指令召喚的實體放進 `Dim::serial_spawns`,配 id 時排在區域產生的實體之後、依指令順序。測試 `tests/summon_order.rs`。
2. **活塞推物品用的是 tick 開始時的進度**(`PistonMovingBlockEntity.tick` 先 `moveCollidedEntities` 才設 `progress = newProgress`)。Kiln 先把方塊實體前進、再推,最後一個 tick 的碰撞形狀變成最終形狀,站在伸出的活塞頭上的物品第二次被推時被擋住(vanilla 0.96 格、Kiln 0.45 格)。
   修正:推之前把進度倒回去,推完再前進(`entity_world::set_piston_progress`)。測試 `tests/piston_items.rs`(物品位置逐 tick 的 vanilla 數字)。
3. 物品**進到移動中的活塞裡面**時,vanilla 用 `Entity.random`(沒有種子)推出去,兩次 vanilla 的結果就不同(24 個場景),不是 Kiln 的差異。

**證據**:
- 物品實體向量(`EntityVectors`,含你列的泡泡柱地板反彈、靈魂沙、仙人掌、活塞旁、藍冰、蜜):**570 個場景全部位元相同**(45 個靜止 500 tick、24 個泡泡柱 300 tick 是新的)。→ 物品物理本身的算術沒有差異。靜止場景一度含「漏斗當地板」3 個,vanilla 在第 5~7 tick 把物品吸走(`removed`),實體測試不模擬漏斗吸取(那是關卡的方塊實體邏輯,由容器向量比),所以拿掉(`EntityVectors.rests` 的 floors 不含漏斗;原檔在 VM 上留為 `items.jsonl.with_hopper`)。
- 活塞向量(`ContainerVectors piston_`:完整關卡 tick,活塞伸出/收回、前面有石頭/史萊姆/蜜/泥土、物品在旁、在上、在前):延伸的 64 個場景 + 收回的 24 個,共 88 個與 vanilla **位元相同**;其餘 24 個是 vanilla 自己兩次結果不同的(第 3 點),用 `VANILLA_NOT_REPEATABLE` 列出、不比。

## 3. 容器裡未知的物品 id

**vanilla(26.3,用 `LoadDropVectors` 量)**:`ValueInput` 是**部分解碼**:
- 未知的 id、沒有 `id`、`Slot` 超出容器(含負數)的項目丟掉;沒有 `Slot` 當 0。
- `count` 缺少或不在 1~99 → 1(65 的石頭保留 65;iron_sword 2 保留)。
- 解不開的元件(未知元件名、值型別錯)只丟掉那個元件,物品留著。
- 束口袋(`bundle_contents`)、潛影盒(`container`)等裡面的物品清單:壞的元素丟掉,其他留著;`ItemStackTemplate` 的 `count` 為 1 時不寫。
- 實體:裝備**逐格**丟掉(盔甲架頭上放未知物品,胸甲留著),`drop_chances` 留著;村民 `Offers` 的壞交易整筆丟掉;掉落物沒有有效物品就移除;展示框變空;拋射物(雪球、藥水、箭…)換成預設物品;載具/驢/羊駝/精靈的容器丟掉壞項目。
- 玩家背包與 `equipment` 同樣。

**Kiln 原本**:「無損」載入——保留原始項目(`undecoded`)並在存檔時寫回,而且 `DataComponentPatch` 把解不開的元件原樣保留;精靈只讀清單的第一項(第一項壞就整個丟)。
**修正**:`ItemStack::from_nbt` 改成部分解碼(`DataComponentPatch::from_value_lenient`,束口袋/潛影盒/`charged_projectiles` 的清單丟壞元素);`ItemList` 不再有 `undecoded`;玩家背包、裝備、箱子礦車、馬、終界箱同改;精靈用 `addItem` 逐一加;拋射物不再保留原始 `Item`;載入時丟過東西的容器標記 `dirty`,區塊裡的副本隨即被改寫。
**證據**:方塊實體 110 個案例(14 種容器 × 7 種壞法 + 單一物品方塊 + 戰利品表)、實體 66 個案例與 vanilla **完全相同**。**測試**:`kiln-item` 的 `saved_items_load_leniently`、`kiln-inventory` 的 `container_items_drop_what_vanilla_drops`;向量 `load_parity.rs` / `load_drops.rs`。
順便:裝飾罐的 `sherds` 在 26.3 是 `{back,left,right,front}` 的物品複合(不是舊的四個 id 的清單),`components.pot_decorations` 保留原樣(不套用);Kiln 原本照原始輸入存(`/setblock` 帶 `sherds:[…]` 會留下 vanilla 會丟掉的資料,物品簡寫不轉成 `{id:…}`),現在依 codec 的形式載入與存出(`/setblock` 6 個案例相同)。

## 4. 中立生物的憤怒

26.3 的存檔鍵是 `anger_end_time`(long,遊戲時間)與 `angry_at`(UUID 的 int 陣列);舊鍵 `AngerTime`(剩餘 tick)讀得進來。
Kiln 已經存 `anger_end_time`,但**沒有存/讀 `angry_at`**(狼、鐵傀儡、北極熊、蜜蜂;終界使者與殭屍豬人本來就有),`AngerTime` 在終界使者/殭屍豬人是「從遊戲時間 0 算」的近似。
修正:`Anger { end, target: Option<Reference>, pending }`:目標存成 `(網路 id 或 UUID)`,載入時只有 UUID、之後用 UUID 找到實體;`AngerTime` 記成 `pending`,在第一次 `updatePersistentAnger` 時變成 `遊戲時間 + 剩餘`(六種中立生物一致)。
**證據**:六種中立生物 × 5 個存檔案例,與 vanilla 存出的複合相同(`load_drops`);`/summon` 帶 `anger_end_time`/`angry_at`/`AngerTime` 的測試 `tests/anger.rs`。

## 5. 非玩家生物身上的箭與蜂針

vanilla:`LivingEntity` 的資料 12、13(箭數、蜂針數)——`AbstractArrow.onHitEntity`(穿透 ≤ 0 時)與 `Bee.doHurtTarget` 加一,`LivingEntity.tick` 在伺服器端每 `20*(30-數量)` tick 掉一個;
配對時只送**非預設值**,數量掉回 0 時要送 0 讓客戶端重設(Kiln 的實體資料送「變動與回到預設的欄位」,所以不需要「永遠送 0」)。
Kiln 原本只有玩家有數量。現在 `MobData` 有四個欄位,`SimLevel::stick_in_body` 對生物也計數,`metadata()` 在數量 > 0 時才送。
**測試**:`player_sync.rs::an_arrow_sticks_in_a_mobs_body_and_falls_out_in_time`(旁觀者收到 `12=1`,580 tick 後收到 `12=0`)。

## 6. 開始追蹤時的屬性清單

`AttributeMap.getSyncableAttributes()` 只有**已經有實例的屬性**,而實例是 `getInstance`(要改它的時候)才建立,讀值不建立。
用 `AttributeVectors` 量 89 種生物:`/summon` 之後 79 種是空的,11 種有 1~3 個(殭屍類、終界使者、史萊姆類、狼),**第一次 tick 之後幾乎都多出 `movement_speed`**。玩家(wp64 在真實伺服器量到)是 4 個:`max_health`、`movement_speed`、兩個互動距離;之後效果/裝備/指令改過的屬性加入。
Kiln 原本:生物把型別的全部可同步屬性都送、玩家 30 個。現在 `Instance.created`(`Attributes::get_mut` 與 `create_for(型別)` 設定;第一次生物 tick 要 `movement_speed`),配對與變動都只列已建立的;生物的變動封包只列變動的屬性(新建立但沒改的不送);玩家 `attribute_lists` 只列已建立的(`attrs_touched` 記下改過的)。
**證據**:89 種生物,新建立時與第一個 tick 之後的屬性集合與 vanilla **全部相同**(`attr_parity.rs`);玩家登入 4 個(`a_player_is_told_of_the_attributes_that_exist`);`crowd_golden` 的封包摘要因此重錄(見最後)。

## 7. 事件順序;同一個 tick 生成又移除的投射物

- 傷害事件對旁觀者原本在**受傷聲音之後**(玩家的 `damaged` 在 tick 結尾的廣播裡排在 `pending_sounds` 之後);改成先傷害事件、再聲音。生物原本就是先傷害事件(兩個一起被當成事件按順序送)。測試 `the_damage_event_comes_before_the_hurt_sound`。
  **沒做**:傷害事件和**不經廣播直接送出的 level event** 的先後(旁觀者的傷害事件仍在該 tick 的廣播裡,level event 直接進出口佇列);玩家自己那份傷害事件本來就是即時送的。
- 同一個 tick 生成又移除的實體(指令召喚的雪球打到地面):vanilla 的追蹤在 tick 開頭配對,所以觀看者收到 `AddEntity` 再收到 `RemoveEntities`;Kiln 的實體追蹤在 tick 結尾,看不到。`track_entity` 對「從來沒被追蹤過就已移除」的實體補送這一對(生成封包用追蹤器記下的初始位置)。測試 `a_projectile_gone_in_its_first_tick_is_added_and_removed`。

## 8. 進行中的突襲在重啟後還在

`raids.dat`(id、已生成波數、不祥之兆等級、狀態、中心、英雄)本來就存、讀。缺的:vanilla 的 `Raider.readAdditionalSaveData` 依 `RaidId` 把襲擊者**放回**突襲(`addWaveMob(wave, raider, false)`:總血量不加,**更新 boss 條**,領隊 `setLeader`);Kiln 讀回 `RaidId` 但突襲不知道,所以重啟後血條是 0。
修正:突襲記下 `known` 襲擊者,第一次看到帶著這個突襲 id 的襲擊者時更新血條並恢復領隊;`joinRaid`(找到突襲的襲擊者)也在每個加入時更新血條(總血量加現有血量,保留 vanilla 的這個行為)。
**測試**:`raids.rs::a_raid_in_progress_survives_a_restart`(真的存檔、關伺服器、重開:id、狀態、波數、不祥之兆等級、中心、襲擊者全數回來並屬於同一個突襲、血條、擊殺後下一波照常出現)。

wp68 的其他持久化項目:
- **離玩家很遠的刷怪籠 `data get block` 是原始存檔**:載入的刷怪籠和存出來的不同(缺預設值)就標記 `dirty`,區塊裡的副本隨即補齊(`mob_spawner::tests::a_spawner_missing_its_defaults_is_rewritten`)。
- **裝飾罐的 `setblock` 資料**:見第 3 項(vanilla 不套用 `components.pot_decorations`,只保留在 `components`;`sherds` 用 26.3 的複合形式)。
- **`difficulty` 重啟後沿用存檔**:不改。vanilla 每次啟動用 `server.properties` 的值(`DedicatedServer.forceDifficulty`);Kiln 沒有 `server.properties`,`KILN_DIFFICULTY` 就是那個屬性,有設就每次啟動套用,沒設就沿用存檔——這是設計選擇,不是漏做。
- **`NoAI` 的牛被栓繩拉過之後 `Motion` 殘留(只是 NBT 的數字,位置不動)**:沒有修;沒有影響行為。

## 9. 重錘與銅工具/盔甲的傷害數字

重錘(重擊、密度、突破、風爆、擊退爆發)與 sweep、各種武器本來就在 `CombatVectors` 的 `MeleeVectors`;這次把銅鎬/銅鏟/銅鋤、銅盔甲(對玩家與對生物、重錘 + 突破)加進去重新量。
**結果**:`combat_parity` 115、`melee_parity` 763、`spear_parity` 148、`mount_parity` 240、`riptide_parity` 110、`enchant_parity` 全部與 vanilla **位元相同**——沒有差異可修。wp68 在真實遊玩中量不出來是時機雜訊,不是 Kiln 的數字。
