分支 `wp81-gaps`(從 main `302681f4` 開出,只推到 `vm`)。做法承襲 wp72~wp79:**比較的兩邊必須是同一個世界**(同種子、同方塊、同時間、同 gamerule、同視野與模擬距離)、
**位元精確的向量優先於統計**、樣本不夠不下結論、每個修正用「關掉它測試必須失敗」的負向檢查(`tools/wp81/neg81.sh`)。所有建置與測試只在 VM(`~/kt wp81-gaps …`,`CARGO_BUILD_JOBS=3~4`),
Kiln 25599、vanilla 25596;Mojang 的資料留在 `work/`,這個套件沒有新增向量檔(證據是並排的鎖步,以及 `tools/wp81/` 的腳本)。

## 1. 區塊票(ticket)

**vanilla**(javap `TicketType`、`TicketStorage`、`DistanceManager`、`ServerChunkCache`、`ThrownEnderpearl`、`ServerPlayer`、`PlayerList`、`Entity.placePortalTicket`):
半徑 `R` 的票讓票所在區塊的等級是 `33 − R`,每遠一格 +1(八個鄰格傳播 = 方形圈);等級 31 以下 = 實體 tick,32 = 方塊 tick,33 = 只載入。

| 票 | 半徑 | 逾時 | 實體 tick | 方塊 tick | 載入 | 存檔 |
|---|---|---|---|---|---|---|
| `forced`(`/forceload`) | 等級 31 | 無 | 那個區塊 | +1 | +2 | 是 |
| `ender_pearl` | 2 | 40 刻 | 那個區塊 | +1 | +2 | 否 |
| `portal`(`placePortalTicket`) | 3 | 300 刻 | +1 | +2 | +3 | 是 |
| `dragon` | 9 | 無 | +7 | +8 | +9 | 否 |
| `player_spawn`(20 刻)、`spawn_search`(1 刻)、`unknown` | | | 只載入(玩家進入與找出生點時) | | | |

* 計時:`purgeStaleTickets` 每刻在實體 tick 之前執行,票的區塊已載入時 −1,**低於 0 才移除**(最後一次更新的那刻起再作用 40 刻,第 41 刻消失);
  同類型同等級的票重放會重新計時。**凍結的遊戲(`/tick freeze`)的空閒刻不執行 `purgeStaleTickets`**(`ServerChunkCache.tick(…, true)` 的條件是 `runsNormally() || !tickChunks`),`/tick step` 的那一刻才算。
  這是在 `ring81.py pearl` 看到的:vanilla 的珍珠區塊在幾秒的凍結空閒刻裡一直在,Kiln 的票在空閒刻裡過期。
* 末影珍珠(`ThrownEnderpearl.tick`):玩家的珍珠,`ticketTimer` 減 1 後 ≤ 0 或換了區塊就放票(半徑 2),計時器設為 39;擁有者在別的維度/別的區域也算(`findOwnerIncludingDeadPlayer`)。
  玩家登出時 `PlayerList.remove` 先存檔(`ender_pearls` 列表,每個珍珠一個複合標籤加 `ender_pearl_dimension`)再以 `UNLOADED_WITH_PLAYER` 移除珍珠;
  登入時 `loadAndSpawnEnderPearls` 把它們放回存的維度並放票。珍珠落地時擁有者傳送到珍珠的位置(任何距離、任何維度)。
* 傳送門票:`TeleportTransition.PLACE_PORTAL_TICKET` 由下界傳送門、終界傳送門、終界閘道使用,在到達的位置放 `portal` 票;珍珠自己穿過傳送門也放。
* 龍:半徑 9(實體 tick 到 7 格),Kiln 原本是 ±8 格都實體 tick 的競技場。

**Kiln 原本**:只有被強制載入的那一格 tick(沒有外面兩圈),沒有珍珠票(珍珠飛出玩家範圍就凍結、擁有者離線時沒有存檔),傳送門只做一次性的 `load_area`(到達的實體在沒有玩家的區塊裡不 tick,下一輪卸載時被存起來)。

**修正**(`tickets.rs`、`blocks.rs::Ticking::add_ticket`、`lib.rs::maintain_chunks`):
`Timed` 票表(傳送門、珍珠;傳送門存進 `chunk_tickets.dat`,格式同 vanilla),`level_tickets(dim)` = 強制區塊(半徑 2)+ 計時票 + 龍(半徑 9);三層 `Ticking` 依半徑加圈;
`maintain_chunks` 把票的中心當玩家自己的區塊(緊急載入)、圈內的區塊由近到遠補載入(每 4 刻看一次)、卸載時保護整個圈;
`projectile.rs::pearl_ticket`(玩家的珍珠放票的事件)、`persist.rs`(登出存檔、登入放回,區塊載入前等待)、`entities.rs`(擁有者不在珍珠的區域時由序列階段傳送:`pearl_landings`)、
`/summon ender_pearl {Owner:[I;…]}` 與存檔載入的投擲物把 `Owner` 對到線上玩家。

**證據**(鎖步,種子 77,視野 5、模擬距離 5):

|---|---|---|

| 傳送門票(`portal` 探針,幼牛穿過傳送門,下界沒有玩家) | 牛的年齡 300 刻後停(票 300 刻,區塊卸載) | 300 刻後找不到 |

測試:`kiln-sim/tests/tickets.rs`(強制載入兩圈、實體/方塊 tick 範圍與水流、方塊 tick 圈邊緣的水流進只載入的圈、珍珠區塊在玩家離開 4000 格時繼續 tick 並讓擁有者回到落點、凍結的遊戲票不倒數、登出/登入帶著珍珠、

## 2. vanilla 載入但不 tick 的圈

**找到的**:玩家的載入票在伺服器視野 `V` 的區塊等級是 31、`V+1` 是 32、`V+2` 是 33(完整載入),與 wp79 相同,但 **Kiln 只載入到 `V` 或 `V+1`**。可觀察的差異:

| 觀察 | 說明 |
|---|---|
| 水/活塞/爆炸從方塊 tick 圈的邊緣寫進外面一圈 | Kiln 的外圈沒載入,水停在邊緣(`simradius81.py` 的 edge 欄:vanilla `11111110`,修前的 Kiln 少一格) |
| `execute if loaded x y z` | vanilla 是**載入票的等級 ≤ 31**(`ExecuteCommand.isChunkLoaded`:`FullChunkStatus.ENTITY_TICKING` 且實體載入),也就是玩家伺服器視野內;模擬距離小於視野時,模擬圈外一格(視野內)仍是 true。Kiln 回答「有載入」(各圈都 true) |
| **自然生怪的候選區塊** | vanilla `collectSpawningChunks` 用 `ChunkHolder.getTickingChunk()`(方塊 tick 狀態,跟著**載入**票:`V+1`),`tickSpawningChunk` 再要求 `canSpawnEntitiesInChunk`(實體 tick 狀態:`V`),與模擬距離無關。wp79 把它當成 `S+1` 圈(S=6、V=8 時 15×15),實際是整個 128 格的圓(`V=8`:每刻 207.6 個區塊),Kiln 少 5.6% |
| 隨機刻 | `forEachBlockTickingChunk` 走模擬追蹤器的實體 tick 區塊再要方塊 tick 狀態:`min(S, V+1)` 圈(S>V 時比實體多一圈) |
| `InhabitedTime` | 方塊 tick 狀態的區塊(`V+1`)+ 玩家在 128 格內 |
| 旁觀者 | `skipPlayer`:不放票(除非 `spectators_generate_chunks`),Kiln 的 tick 範圍仍算旁觀者 |

**修正**:載入半徑一律 `V+2`(`region.rs::LOADED_BEYOND_VIEW`),`Ticking` 加 `loading_block`(狀態層,`V+1`)與 `random`(`min(S, V+1)`),生怪候選用 `visible ∩ 128 格`、`InhabitedTime` 用 `loading_block`,
`execute if loaded` 用載入票的等級(`commands.rs::is_chunk_ticking`),旁觀者不放票。

**證據**:`simradius81.py`(S=4,V=5 與 S=V=5):`execute if loaded` 在 S<V 時 vanilla 到 V(`11111100…`),水源放得進去的區塊 K = V = `11111111`(到 V+2),邊緣的水 K = V = `11111110`;
`spawn_ring.rs`(S=3,V=8:嘗試的區塊到 8 格、9 格沒有,vanilla 的同一個設定也是);每刻候選區塊數(沒有上限的 AMBIENT 類別)修前 K 195.9 / V 205.5,修後 **K 205.3 / V 205.5**。

**代價**:每位玩家多載入的區塊 `(2V+5)²` 對 `(2V+1)²`(V=10:625 對 441,+42%),只多記憶體與產生時間,不增加 tick 時間(外面的圈不 tick)。`crowd_golden` 的狀態雜湊與封包摘要都沒變。

## 3. 下界屋頂的豬布林(殘差)

並排的 `farm81.py nether`(種子 77、模擬距離 6、視野 8、屋頂平台 15×15、600 刻一回合,回合末清掉全部生物),新增計數器後逐刻統計(`sumctr81.sh`;「啟用刻」= 全域怪物上限未滿的刻):

| | 修前 K(51 回合) | 修後 K(30 回合) | V(30 回合) |
|---|---|---|---|
| 沒有上限的類別(AMBIENT)每刻嘗試的區塊數 | 193.9 | **205.3** | **205.5** |
| 啟用刻比例 | 10.65% | 10.19% | 9.18% |
| 每個啟用刻的怪物類別區塊檢查(含上限拒絕) | 186.3 | 202.2 | 191.7 |
| 每個啟用刻的挑選(`pick`) | 194.0 | 210.9 | 198.4 |
| 每個啟用刻的有效位置(`validPosition` 真) | 1.225 | 1.208 | 1.269 |
| 每個啟用刻的生怪(`validMob` 真) | 1.071 | 1.087 | 1.119 |

* **找到並修掉一個機制差異**:自然生怪的候選區塊(第 2 項):vanilla 是整個 128 格的圓(跟著**視野**而不是模擬距離),Kiln 只到 `S+1` 圈,每刻少 5.6% 的區塊(193.9 對 205.5);修後 205.3 對 205.5。
* 第一次的判斷(wp79 的「15×15 對 13×13」)只比較了兩個方形,沒有看到這個圓;`spawn_ring.rs` 現在用 S=3、V=8 驗證嘗試的區塊到 8 格、9 格沒有。
* 啟用刻比例:vanilla 自己四次獨立的跑是 7.5%、7.6%、8.3%、9.2%;Kiln 是 9.2%、9.1%、8.8%、10.7%(修前)、10.2%(修後)。**vanilla 自己的變異範圍(7.5~9.2%)涵蓋差異的一半以上**;
  差異的符號八次一致,但每次的啟用刻只有 2 000~10 000(每回合約 70 個),要把它壓到 ±5% 以內需要好幾個小時的並排跑,這個套件沒有做。沒有找到其他機制來源。
* 平台上的殭屍豬人:修前 30 回合 K 36 對 V 32(0.5σ);修後 K 25(30 回合)。wp79 的「+30%」在雜訊內。
* 另兩個下界生物群系(第 5 項)K/V 的殭屍豬人普查符號相反(靈魂沙谷 85 對 53、玄武岩三角洲 48 對 79):**沒有系統性的偏多**。
* 沒有解釋的:修後 Kiln 的怪物類別檢查比 vanilla 多 5%(202.2 對 191.7),而 vanilla 這個數字低於它自己的候選區塊數(205.5):啟用的刻裡 vanilla 有約 7% 的候選區塊沒有被問到,原因不明。

結論:找到一個真的機制差異並修掉;剩下的 K/V 差異在雜訊邊緣,沒有找到其他來源。
