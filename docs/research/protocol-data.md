# protocol-data: Minecraft Java Edition protocol and game-data state, September 2026 (for a from-scratch Rust server)

## Current version and cadence (verified 2026-09-26)
- **Latest release: Java 26.3, "Wilderness Bound", released 2026-09-15. Protocol 777, data (world) version 5023, data pack 121.0, resource pack 97.1, requires Java 25.** I confirmed this from Mojang's version manifest and from `version.json` inside the official server.jar. The newest snapshot is `26.4-snapshot-1` (2026-09-22): protocol 0x40000153 (1073742163), world version 5119.
- **Naming.** Mojang announced a new scheme on 2025-12-02: `YY.D.H` (year, drop number, hotfix). 1.21.11 (protocol 774, 2025-12-09) was the last 1.x release. 26.1 "Tiny Takeover" (775) came out 2026-03-24, 26.2 "Chaos Cubed" (776) on 2026-06-16, and 26.3 (777). Snapshots are now named `26.x-snapshot-N`, alongside `-pre-N` and `-rc-N`. Snapshot protocol numbers are `0x40000000 | n`. Bedrock also uses year numbering now (26.50 = Wilderness Bound), but its protocol numbers are separate (2193).
- **Cadence.** There are about 4 drops a year: 2025 had 1.21.5, .6, .9 and .11; 2026 has 26.1, .2, .3, with .4 in development. **Every drop changes the protocol number.** Hotfixes usually keep it (26.1.1 and 26.1.2 stayed at 775), with exceptions (1.21.7 moved to 772 thirteen days after 1.21.6). The churn inside one drop is large. I diffed the data-generator output between 26.2 and 26.3:
  - 3 clientbound packets added in Play and 1 in Configuration; serverbound `swing` replaced by `punch`.
  - 104 clientbound Play packet IDs moved.
  - About 95% of item IDs and 98% of block IDs moved.
  - Block states grew from 32,366 to **35,723**, so the global (direct) block palette went from **15 to 16 bits**.
- **Obfuscation is gone.** Announced 2025-10-29. Unobfuscated experimental jars shipped alongside 25w45a through 1.21.11. Starting with 26.1 Snapshot 1 the jars are fully unobfuscated and no mappings are published (the 26.3 version JSON has only client/server downloads). I checked that class names are readable, for example `net.minecraft.network.Varint21FrameDecoder`, `world.level.chunk.PalettedContainer`, `chunk.storage.RegionFile`. `javap` against the official jar is therefore a practical primary source.

## Wire framing, from vanilla 26.3 bytecode
- Frame: `VarInt length` (at most 3 bytes, so at most 2,097,151) + `VarInt packetId` + body.
- Compression turns on after `Set Compression` (threshold VarInt; negative or absent means off; the vanilla default `network-compression-threshold` is 256). Compressed frame: `VarInt packetLen`, `VarInt dataLen` (0 means not compressed), then zlib data. `CompressionDecoder` caps compressed length at 2,097,152 and uncompressed length at 8,388,608. The vanilla server rejects compressed packets smaller than the threshold.
- Encryption: RSA-1024 key exchange (the public key is sent as X.509 SubjectPublicKeyInfo DER), a 16-byte shared secret, then **AES-128/CFB8 with key = IV = secret**. The cipher runs continuously across packets and encrypts everything, including the length prefix.
- Online-mode authentication: the server calls `GET https://sessionserver.mojang.com/session/minecraft/hasJoined?username=&serverId=<mc-hex-sha1(serverId‖secret‖pubkeyDER)>[&ip=]`. The hash is Minecraft's signed two's-complement hex, not standard hex.
- authlib 10.0.77, bundled with 26.3, now resolves its endpoints from `https://discovery.minecraftservices.com/minecraft/client`. That document currently still points `verify` at sessionserver and lists `publickeys` at api.minecraftservices.com.

## State machine for 26.3
- **Handshake** `intention`: protocol VarInt, host String(255), port u16, intent 1=status, 2=login, 3=transfer. `accepts-transfers` defaults to false. The legacy 0xFE ping must also be handled.
- **Status**: 2 packets each way.
- **Login**: `hello` → `Encryption Request` (with a `should authenticate` flag) → `key` → optional `Set Compression` (must come before success) → `login_finished` (GameProfile + a **Session ID UUID, new in 26.2**) → `login_acknowledged`. Also `custom_query` (the channel proxies use) and `cookie_request`/`cookie_response` (at most 5 KiB).
- **Configuration**: 21 clientbound and 10 serverbound packets: brand, `client_information`, `update_enabled_features`, `select_known_packs` in both directions, one `registry_data` per synchronized registry, `update_tags`, `finish_configuration`/ack. It also carries resource packs, cookies, `transfer`, `server_links`, dialogs, `code_of_conduct`, `custom_report_details`, and in 26.3 `post_effects`.
- **Play**: 144 clientbound and 69 serverbound packets. Play can go back to Configuration through `start_configuration` / `configuration_acknowledged`. Keep-alive: the server kicks after 15 s; the client times out after 20 s.
- **Upcoming in 26.4-snap1:**
  - The intention host field becomes up to 1024 chars and URI-query-style (`host?k=v&…`, keys starting with `_` reserved, `_o` holds the original SRV host, `<id>@<host>` maps to `_id`).
  - `transfer` gains a properties map.
  - A `minecraft:mod_list` payload is added.
  - **Biomes become per-block.** In the snapshot jar the biome paletted container is 16³ = 4096 entries on disk and on the wire (bpe 1–4 linear, 5–8 hashmap, above 8 global), and the chunk NBT field `Status` is renamed `status`.

## Registries and known packs
- The client gets about 30 synchronized registries, among them `dimension_type`, `worldgen/biome`, `damage_type`, `chat_type`, `enchantment`, `painting_variant`, `jukebox_song`, `instrument`, trims, `dialog`, `timeline`, `world_clock`, `sulfur_cube_archetype`, test_*, and cat/chicken/cow/frog/pig/wolf/zombie_nautilus variants plus their sound variants. The client requires certain entries: `plains`, 26 named damage types, specific trims, jukebox songs, chicken variants, and certain tags.
- **Known packs.** The server offers `minecraft:core` with version = game id (for example "26.3"). If the client echoes it, `registry_data` may omit the NBT, but every entry ID must still be listed, because list order assigns the numeric IDs. Tags are always sent in full (883 vanilla tag files). From bytecode: vanilla uses the known packs only when the client's reply equals the server's list exactly; otherwise it sends everything.

## Chunks
- **Wire section layout:** `short nonEmptyBlockCount`, `short fluidCount` (present in 26.3 per bytecode), block container of 4096 entries, biome container of 64 entries (4096 in 26.4-snap).
- **Paletted container:** `u8 bpe` + palette + a long array whose length is **not sent (since 1.21.5)** and is computed as ceil(n / floor(64/bpe)); entries never span two longs.
- **Blocks:** bpe 0 is single-valued (VarInt); 1–8 is indirect (1–4 is treated as 4, linear palette; 5–8 hashmap); above 8 is global at ceillog2(#states) = **16 in 26.3**.
- **Biomes (26.3):** 0, 1–3, else global.
- **Heightmaps:** array of (VarInt type, long[]) using types 1, 4, 5, not NBT (since 1.21.5).
- **Light:** 4 BitSets plus 2048-byte arrays, covering the world's sections plus 2.
- **Flow control:** `chunk_batch_start` / `finished` / `received` (client-reported chunks per tick). Bundles are capped at 4096 packets. The chunk buffer is capped at 2 MB.
- **On disk it is still Anvil.** 4 KiB sectors. Header: a 1024-entry location table (3-byte offset, 1-byte count) and a timestamp table. Each chunk: 4-byte length + compression byte (1 gzip, 2 zlib [default], 3 none, 4 LZ4, 127 custom + u16-length name; +128 means stored externally in `c.x.z.mcc` when over 255 sectors). `region-file-compression` defaults to deflate.
- **26.1 moved the world layout:** `dimensions/minecraft/{overworld,the_nether,the_end}/{region,entities,poi}`, `players/{data,advancements,stats}`, namespaced `data/minecraft/*.dat`.

## Data sources
- **Built-in data generator.** `java -DbundlerMainClass=net.minecraft.data.Main -jar server.jar --reports --server` took 15 s and wrote 10,038 files:
  - `reports/blocks.json`: 1286 blocks / 35,723 states with IDs.
  - `registries.json`: 95 built-in registries with protocol IDs.
  - `packets.json`: IDs only, no field layouts.
  - `commands.json`, `datapack.json` (registry metadata), `json-rpc-api-schema.json` (OpenRPC, the server management protocol 3.1.0, 89 methods), `biome_parameters/`, `minecraft/components/item/*.json` (default components for 1658 items).
  - With `--server`: the full vanilla data pack (worldgen, registries, loot, recipes, tags).
  - Not included: collision shapes, structure `.nbt` templates (1710 of them sit inside the jar), and packet field layouts.
- **PrismarineJS minecraft-data** covers up to 26.1 (added 2026-07-28, about 4 months after release); 26.2 and 26.3 are still missing. Past lag has been 2–4 months. It is still useful for `blockCollisionShapes.json` and a machine-readable `protocol.json`.
- **Pumpkin's Extractor** (a Fabric mod, already on 26.3) fills the gaps. **pokechu22 Burger** output for 26.3 no longer contains blocks or packets.
- The **minecraft.wiki Packets page** documents 26.3 / 777; its Chunk-format table still says 15 bits for the direct block palette.

## Proxies, multi-version, Bedrock
- **Proxies.**
  - Velocity (supports up to 26.3) modern forwarding: the backend sends Login Plugin Request `velocity:player_info` with one byte = the maximum forwarding version (1–4). The reply is HMAC-SHA256 (32 bytes) + VarInt version + address + UUID + name + properties.
  - BungeeCord legacy forwarding: `host\0ip\0undashedUUID\0propertiesJSON` in the handshake host field. Spigot/Paper raise the host limit from 255 to 32767; BungeeGuard adds a token property.
- **Multi-version.** ViaVersion 5.12.0 (2026-09-18) added 26.3 clients three days after release. It chains per-version-pair protocol steps (`v26_2to26_3`) driven by generated mapping files. Its chunk rewriting is the main CPU cost; its 5.11.0 notes claim chunk read/write got up to 90% faster. I found no absolute published numbers.
- **Bedrock.** RakNet over UDP 19132; 0xFE batches; compression negotiated as flate, snappy or none; ECDH P-384 + AES-256-CTR (IV = key[0:12] ‖ 00000002) with an 8-byte SHA-256 checksum; login is a JWT chain plus an OIDC token. Mojang publishes official JSON schemas (`Mojang/bedrock-protocol-docs`, now at 1.26.60 previews). Geyser bridges to Java (Java 26.3 support is still an open PR). In Rust: bedrock-rs, rust-raknet, and Pumpkin's work-in-progress Bedrock support.

## Design implications
- Never hardcode packet IDs, block-state IDs, item IDs or registry IDs. Generate Rust tables at build time from the vanilla generator output (packets.json, blocks.json, registries.json, the default item components, the data pack) for one pinned version. Keep one version folder per protocol (e.g. data/777/) so another version can be added later. One drop shifted 104 clientbound packet IDs and about 98% of block IDs.
- Store block-state IDs as u16, not i16 or 15-bit types. 26.3 has 35,723 states and the direct palette is 16 bits. Compute direct bpe as ceillog2(state_count) and biome direct bpe from the biome registry that was actually sent; never use constants. Add a build-time assertion that the state count stays under 65,536.
- Keep chunk sections in memory in the vanilla paletted format (single / linear up to 4 bits / hashmap 5–8 / global) so serializing a section to the network is mostly a memcpy. Write long arrays so no entry crosses a long boundary, and compute the array length rather than storing it. Keep fluidCount and nonEmptyBlockCount as cached counters.
- Make the biome container dimensions a per-version parameter. 26.3 uses 4×4×4 (64 entries); 26.4-snapshot-1 uses 16³ (4096) on the wire and on disk with a new palette table. Keep a separate noise-biome grid for worldgen, as vanilla now does.
- Use a table-driven connection state machine (Handshake → Status | Login → Configuration ⇄ Play). Configuration must be re-enterable from Play (start_configuration) to support proxies and data-pack reloads. Treat Transfer (intent 3), cookies and Velocity's login-plugin exchange as first-class features.
- Per-connection pipeline: a 3-byte VarInt frame decoder, then zlib (use libdeflater for whole-buffer packets; stay under the 2 MiB compressed / 8 MiB uncompressed limits; reject compressed frames below the threshold), then AES-128-CFB8 with a continuous cipher state (RustCrypto `aes` + `cfb8`). Encryption is serial per stream, so run it on the connection's network task, not the game tick. Serialize a chunk once, compress it once, and share the bytes across viewers where possible; per-connection encryption still has to run per viewer.
- Registry sync: support both paths. First, known packs `minecraft:core` = the exact game version, sending the entry lists without NBT (vanilla takes this path only when the client's reply matches the offered list exactly). Second, full NBT for custom data packs or mismatched clients. Embed the vanilla data-pack JSON, convert it to nameless-root network NBT at startup, cache the encoded registry_data and update_tags packets, and reuse the cached bytes for every login.
- Online mode: fetch endpoints from discovery.minecraftservices.com, with the hardcoded sessionserver URL as a fallback. Implement Minecraft's signed hex SHA-1. Run hasJoined asynchronously off the tick thread. Cache the Yggdrasil public keys from /publickeys to verify texture-property and chat-session signatures.
- Proxy support should cover Velocity modern forwarding (HMAC-SHA256, version 4 / LAZY_SESSION, constant-time compare) and BungeeCord legacy / BungeeGuard, which requires accepting a handshake host of up to 32767 characters. Also parse the 26.4 `host?k=v` query format, with reserved `_` keys, so upgrading to 26.4 does not break the handshake path.
- Multi-version: do not build it into the core for v1. Run latest-only and point users to ViaVersion/ViaProxy in front, as Pumpkin does. If native multi-version is added later, place it at the protocol edge as ID-remap tables generated from each version's reports, remap palette entries only (cheap), fall back to a full repack when the direct bpe or biome dimensions differ, and ship per-version registry NBT. Each supported version requires its own full data set.
- World storage: implement Anvil read/write, including LZ4 (4), external .mcc files, and the 26.1 layout under dimensions/minecraft/*/{region,entities,poi} and players/*. Check chunk DataVersion. Do not implement DataFixerUpper; require worlds to be upgraded with vanilla `--forceUpgrade` first. A custom format (Linear-style whole-region zstd) can be an optional backend behind a trait.
- Data pipeline: a CI job downloads the server.jar from the Mojang manifest, verifies its sha1, runs `--reports --server`, extracts data/minecraft/structure/*.nbt from the inner jar, and runs a small Fabric extractor mod or the Pumpkin Extractor for collision shapes and entity metadata. Do not depend on minecraft-data for new versions: it lags 2–4 months and has no 26.2/26.3 data. Burger's hosted output is no longer usable. Since packets.json has no field layouts, hand-write codecs (or use derive macros) checked against the unobfuscated vanilla StreamCodecs and the minecraft.wiki Packets page.
- Plan for about 4 protocol breaks a year, each arriving with 10+ snapshots of warning. Budget a release engineering task per drop (codegen rerun, packet diff, registry diff). Consider tracking snapshots on a branch, since snapshot protocol numbers are 0x40000000 | n.
- Bedrock: treat it as a separate front end (RakNet over UDP, little-endian, hashed block IDs available) behind the same world core, or rely on Geyser. The two protocols share almost nothing at the wire level. Mojang's official Bedrock JSON schemas make codegen easier there than on Java.

## Open questions
- Will 26.4's per-block biome storage (4096 entries per section) survive to the final 26.4 release, and will Chunk Biomes (`chunks_biomes`) and the other biome packets change the same way? Check the 26.4 pre-releases.
- How exactly does the client read a global-palette bpe that differs from ceillog2(registry size) (Configuration$Global bitsInStorage vs bitsInMemory, alwaysRepack)? For example, can a server send 15-bit direct sections when no ID is at or above 32768? This needs a decompiled PalettedContainer.createOrReuseData or an empirical test.
- What is the vanilla CRC32C hashing algorithm for Hashed Slot components? The wiki says it is undocumented; it has to be ported from HashOps in the unobfuscated jar.
- Which version added the fluidCount short to the wire chunk section? It is confirmed present in 26.3 and 26.4-snapshot-1 bytecode but not dated; it matters if multi-version support down to 1.21.x is ever wanted.
- How will Velocity, BungeeCord and Paper handle the 26.4 query-string host field alongside legacy `\0` forwarding, and will vanilla's `allowed-connection-ids`/_id become a standard way to route virtual hosts?
- There are no published absolute CPU or latency numbers for ViaVersion translation or for AES-CFB8 plus zlib per connection. These need benchmarking with a Rust prototype (e.g. MB/s per core for cfb8 with AES-NI, libdeflate at level 6 on typical chunk packets).
- What is the actual wire size of the 26.3 registry_data and update_tags set, with and without known packs, compressed? JSON sizes were only estimated (about 450 KB for registries, 223 KB for tags); measure this by capturing a vanilla login.
- Can a server advertise several minecraft:core versions (e.g. 26.1, 26.1.1, 26.1.2) in Known Packs so that hotfix-mismatched clients with the same protocol still avoid full NBT? Pack stacking semantics make this uncertain; it needs testing.
- Is there a stable, maintained public source of block collision shapes for 26.2 and 26.3 other than running an extractor mod ourselves? minecraft-data has only up to 26.1.

## Omissions
- 26.3 has 32 synchronized registries, not the 29 the report lists. The three new ones are decorated_pot_pattern, block_transformer and worldgen/block_state_provider. Drops add whole registries, so the configuration-phase registry list must come from the jar (RegistryDataLoader.SYNCHRONIZED_REGISTRIES / datapack.json) at build time.
- Configuration-state packet IDs move between drops as well. In 26.2→26.3, inserting post_effects at 0x0A moved 10 of the 20 clientbound configuration packets. Every connection state needs codegen'd IDs, not only Play.
- The report's open question about direct-palette bpe can be answered from bytecode. The client builds Configuration$Global(bitsInMemory, wireBpe) and reads storage at the wire width, so any direct bpe of 9 or more that fits the IDs is accepted. That lowers the cost of repacking in a multi-version layer.
- Vanilla has a 30 s netty ReadTimeoutHandler in addition to the 15 s keep-alive challenge. The 20 s client timeout the report cites comes from the wiki; the client jar was not checked.
- authlib 10.0.77 has no hardcoded sessionserver fallback, so vanilla auth depends entirely on the discovery document. Caching the discovery document (with a TTL) is worth considering.
- Secure chat is not covered: chat_session_update, player chat-key validation against /publickeys, the signed-message chain and last-seen acknowledgements, and enforce-secure-profile. Whether to implement signed chat or run unsigned (system chat only) is a major design decision for the chat pipeline and for client warnings.
- Network text components have been NBT (not JSON) since 1.20.3. They appear in many packets (chat, titles, item names, dialogs), so the core needs an NBT text-component codec alongside its NBT registry codec.
- Custom payload size limits are asymmetric: 32767 bytes serverbound and 1 MiB clientbound. They matter for plugin-channel and proxy messaging.
- Pumpkin's default Anvil compression is LZ4 while vanilla's is deflate. Vanilla can read LZ4 (ID 4), but external tools that assume zlib may fail on worlds written that way.
- Velocity's native crypto and compression acceleration exists only on Linux and macOS. Proxy or throughput numbers measured on Windows (the user's dev OS) use the Java fallback and should not be compared directly with Linux figures.

BungeeGuard appends a `bungeeguard-token` property carrying the shared secret. Spigot/Paper patch ClientIntentionPacket to readUtf(Short.MAX_VALUE) and validate with HOST_PATTERN `[0-9a-f\.:]{0,45}` and PROP_PATTERN. BungeeCord ProtocolConstants lists 26.1 (775), 26.2 (776) and 26.3 (777). The mechanism is insecure without firewalling or BungeeGuard. The 26.4 query-string host format (up to 1024 chars, `?k=v`) may interact with `\0`-delimited forwarding; how proxies will handle this is unverified. - (medium, TS) ViaVersion-style multi-version support means chaining per-version-pair translators that remap every numeric ID space and rewrite chunks, items and registries. ViaVersion adds support a few days after each release. :: ViaVersion 5.12.0 (2026-09-18) added 26.3 clients three days after release. Protocol modules exist per pair (…, v1_21_9to1_21_11, v26_1to26_2, v26_2to26_3). Mappings are generated from each server jar by ViaVersion/Mappings (MappingsGenerator) and compiled into compact NBT diffs. Release notes name chunk read/write as 'most of Via's packet handling': 5.9.1 improved it, and 5.11.0 claims up to 90% faster chunk read/write. I found no absolute published CPU or latency numbers (unverified). The costs follow from the churn above: packet IDs, block states (palette-entry remap is cheap for indirect sections, but a direct 16↔15-bit palette or 26.4's 4096↔64 biome change needs a full repack), items with data components (122 types, formats change), entity metadata indices, sound and particle IDs, and per-version synchronized-registry NBT. An older client cannot use `minecraft:core` 26.3 from known packs, so it must receive full registry NBT in its own schema. [https://github.com/ViaVersion/ViaVersion/releases/tag/5.12.0 https://github.com/ViaVersion/ViaVersion/releases/tag/5.11.0 https://github.com/ViaVersion/Mappings]
- (medium, TS) Item stacks: containers use a 'Hashed Slot' format in which component values are CRC32C checksums, and the wiki does not document how they are computed. :: The Click Container serverbound packet sends item components as CRC32C hashes (since 1.21.5). The wiki states the hash generation is undocumented. Implementers must copy vanilla's HashOps encoding from the unobfuscated jar. Normal slots send a data-component patch against per-item defaults, and those defaults are available from the generator's reports/minecraft/components/item/*.json. 26.3 has 122 data_component_type entries. [https://minecraft.wiki/w/Java_Edition_protocol/Slot_Data https://minecraft.wiki/w/Java_Edition_protocol/Data_types]
- (high, TS) Vanilla dedicated servers expose the Minecraft Server Management Protocol: JSON-RPC 2.0 over WebSocket, version 3.1.0 in 26.3, disabled by default. :: Added in 1.21.9 (25w35a). Relevant server.properties: management-server-enabled=false, host=localhost, port=0, secret, tls-enabled=true, allowed-origins. Clients authenticate with a Bearer token or `Sec-WebSocket-Protocol: minecraft-v1,<secret>`. The generator writes an OpenRPC schema with 89 methods (allowlist, bans, ip_bans, players, operators, server/status|save|stop|system_message, serversettings/*). A compatible core could implement it so existing tooling works. [https://minecraft.wiki/w/Minecraft_Server_Management_Protocol https://minecraft.wiki/w/Java_Edition_26.3]
- (medium, TS) Bedrock uses RakNet over UDP 19132, 0xFE batches, negotiated compression, ECDH P-384 + AES-256-CTR, and a JWT/OIDC login. Mojang publishes official JSON protocol schemas. The current release is 26.50/26.51 (internally 1.26.5x, protocol 2193). :: Transport: RakNet on UDP 19132, game packets batched behind the 0xFE header. NetworkSettings negotiates compression threshold (u16) and algorithm (0 flate, 1 snappy, 0xFFFF none). Encryption: AES-256-CTR with IV = key[0:12] ‖ 00 00 00 02, plus an 8-byte SHA-256(counter ‖ payload ‖ key) checksum (gophertunnel encoder.go). Login: a certificate JWT chain plus an OIDC ID `Token`, which gophertunnel verifies with an oidc verifier. Values are little-endian with zigzag VarInts. StartGame has UseBlockNetworkIDHashes so multi-version servers can use hashed block IDs. Version history: 1.21.130 (898) → 26.0 (924) … 26.30 (1001) → 26.40 (2168) → 26.51 (2193). Mojang/bedrock-protocol-docs was updated to 1.26.60-preview.28 on 2026-09-22 and includes AntiCheatServer, NetherNet and SubChunk request guides. Geyser supports Bedrock 26.30–26.51 and Java 26.2; its Java 26.3 PR is open. Rust options: bedrock-crustaceans/bedrock-rs (187 stars, active), b23r0/rust-raknet (225 stars, active), Pumpkin's work-in-progress Bedrock support. The main reference server is Go: df-mc/dragonfly. Java 26.2 also added P2P friend/LAN joining (ICE, with LOCAL/DIRECT/RELAY paths); this does not affect dedicated servers.
