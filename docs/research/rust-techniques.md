# Rust techniques and crates for a high-performance Minecraft Java Edition server core (state as of 2026-09-26)

## Scope and method
I read the source (via `gh api`) of the active Rust Minecraft servers: **Pumpkin** (11.3k stars, pushed 2026-09-25, targets 26.3), **Hyperion** (pushed 2026-09-24, 26.2), **FerrumC** (1.21.8), **Valence** (maintenance only, still MC 1.20.1 on bevy_ecs 0.14) and **azalea** (bot client, 26.2). I got crate versions from the crates.io API. I also ran **local microbenchmarks** on the developer's machine (Ryzen 7 5700X3D, Windows 11, rustc 1.97, fat LTO, one thread). The benchmark used real chunk data: 1024 chunks, 42.9 MB of raw NBT, decompressed from a 26.x `r.0.-1.mca` found in the local `.minecraft` saves. - **AES-128-CFB8 is the real CPU hog.** The `cfb8` 0.9 + `aes` 0.9 crates run at about **50 MB/s per core** for both encrypt and decrypt. OpenSSL 3.5.6 does 36 MB/s on the same machine, while AES-128-CTR does 8.8 GB/s.
- **Decryption can be batched.** Each keystream byte is `AES(previous 16 ciphertext bytes)[0]`, and all those inputs are already known. Feeding them to `encrypt_blocks` measured **~295 MB/s, about 6x faster**. The output was checked against the crate.
- **Encryption of one stream is inherently serial.** Interleaving 4, 8 or 16 independent connections per thread ("multi-buffer", the technique Intel uses for CBC) measured **122–186 MB/s per thread, about 3–4x**, using naive code.
- **Allocator on Windows.** mimalloc beat the Windows system heap by 2.7x on one thread and 4.1–4.3x on 8–16 threads. `tikv-jemallocator` does not support MSVC.
- **Rough cost of one player joining.** At view distance 10 (441 chunks) with no caching: about 120 ms of CPU to compress at L4 and about 60 ms to encrypt. At view distance 32 (4225 chunks) it is about 1.1 s plus 0.56 s. These are estimates, because NBT is not the wire format.

## Recommendations by area
1. **Networking.** Default to tokio (multi-thread runtime) with separate read and write tasks per connection. The game tick never awaits. Each tick, one contiguous `BytesMut` per player collects every packet, so there is one write per connection per tick (the same idea as Netty flush consolidation). Use a queue bounded by bytes, not by packet count; exceed it and the client is disconnected (Valence's `byte_channel` design; Pumpkin disconnects at 64 MiB pending). Run CPU work such as compression on rayon or dedicated threads, not `spawn_blocking` (the 10–100 µs-between-awaits rule).
   - Skip io_uring for now. No Rust MC server uses it, tokio's io_uring support is unstable and file-only, and Docker/containerd's default seccomp profiles block io_uring.
   - Alternative: compio (IOCP on Windows, io_uring on Linux, thread-per-core).
   - Avoid glommio and monoio: they target Linux, and the developer works on Windows.
2. **Packets.** Use derive macros plus IDs generated from extracted data.
   - Valence: `derive(Encode, Decode, Packet)`, with the ID resolved from the struct name to a generated constant.
   - azalea: `derive(AzBuf)` with `#[var]` field attributes; the state tables are generated by Python.
   - Pumpkin: `#[java_packet(CONST)]` plus a hand-written writer for each protocol version.
   - Prefer decoded packets that own their data through `bytes::Bytes` over zero-copy decoding with lifetimes. Hyperion's Valence fork removed the lifetime from `Decode` because borrowed packets that outlive their handler were unsound.
   - 26.1 was the first unobfuscated release. Even so, Hyperion could generate only 124 of 256 packets mechanically. ItemStack and its 111 data components, plus entity metadata, remain hand work (their estimate: 15–20k lines).
3. **Compression.** For wire compression, libdeflater at L1–L4 is best on both speed and size. It needs whole buffers, which is fine because each packet header carries its uncompressed length. It builds on MSVC via `cc`. For a pure-Rust option, use flate2 with `zlib-rs`. Avoid miniz_oxide (Pumpkin's current choice); it is 2–2.6x slower at L6. `zlib-ng` failed to build here because CMake/MSBuild hit the 260-character path limit.
   - Reuse the `Compress` state: 4.95 µs versus 12.0 µs per 300 B packet.
   - Cache each chunk's compressed, framed packet until the chunk changes (Valence's `cached_init_packets`). Encode once and memcpy to every viewer (Valence's `Messages` buffer).
4. **Encryption.** Measure first. Batched decryption is simple and safe to add. Multi-buffer encryption is an optimization for a later phase. When the server runs behind Velocity, the backend link is normally unencrypted, so the cost moves to the proxy.
5. **ECS.** The ecosystem is volatile.
   - bevy_ecs 0.19.1 is the only large, well-maintained option (used by FerrumC and azalea).
   - flecs-rust has safety and maturity problems. 0.2.2 is the only non-yanked release, and Hyperion needs git main for a double-free fix. flecs 4.1 also forbids creating entities inside multithreaded systems.
   - Hyperion switched flecs → bevy (July 2025) and then reverted to flecs (July 2026).
   - evenio has been dead since 2024. Valence stalled on bevy 0.14.
   - Pumpkin uses no ECS: `Arc` objects, atomics, `ArcSwap`, and rayon `par_iter` over worlds and players on a dedicated tick thread.
   - Recommendation: bevy_ecs used standalone inside each region's tick, or a custom structure-of-arrays layout for hot data. Watch executor overhead: an old issue measured 470 µs per executor call with more than 1000 systems.
6. **Parallelism.** Folia-style regions (N×N chunk sections, a merge-radius invariant, regions that cannot grow while ticking) give data-parallel ticks. Hyperion takes the other route: fan-out to players happens in horizontally scaled proxies, so broadcast work on the game server is O(n) instead of O(n²). Use arc-swap for snapshots and dashmap or papaya for concurrent maps. Size the tokio, rayon and bevy_tasks thread pools explicitly so they do not oversubscribe the CPU.
7. **Memory.** mimalloc on both platforms (jemalloc on Linux only if profiling proves it better). Use per-tick arenas (bumpalo) for scratch data. For block sections, use palette containers with Single / Indirect (u8 or nibble indices) / Direct (u16) variants and bit-pack only when serializing. That is Pumpkin's and Valence's choice: it trades memory for fast get/set. `std::simd` is still nightly-only. Rust 1.87 made most `std::arch` intrinsics safe inside `#[target_feature]` functions. `pdep`/`pext` are slow on Zen1/Zen2, so use runtime dispatch.
8. **Storage.** Anvil for compatibility (LZ4 option since 24w04a; custom type 127 since 24w05a). Measured here: 27% of the Anvil file is sector padding. Whole-region zstd compresses to 15.4% at L3 and 10.8% at L19, which means Linear's "~50% smaller" comes mostly from removing padding plus using high zstd levels. Pumpkin supports Anvil, Linear and its own "pump" format; FerrumC uses LMDB (heed).
9. **Worldgen.** Compile density functions:
   - build-time codegen or monomorphized generics (Pumpkin's `StaticDensityFunction`),
   - JIT to JVM bytecode on the Java side (C2ME's DFC: +90% with Tectonic),
   - vectorize across sample positions.
   - The SIMD noise crates are stale and not bit-exact with vanilla.
10. **Observability.**
   - Profiling: `tracing` + `tracing-tracy`/Tracy (used by Hyperion and FerrumC) and samply (Windows ETW or Linux perf).
   - Async and metrics: tokio-console (needs `tokio_unstable`) and metrics + Prometheus.
   - Testing tools: azalea swarms (version-locked to the protocol, so keep them in a separate workspace like FerrumC), Hyperion's lightweight rust-mc-bot, and cargo-fuzz (needs nightly, works on Windows).
   - Test methods: coverage-guided codec fuzzing and Hyperion-style tick-by-tick differential tests against recorded vanilla traces.

## Design implications
- Networking default: tokio multi-thread runtime; separate reader and writer tasks per connection; the game tick never awaits and only pushes one per-player BytesMut per tick (or per flush window) to the writer. Keep compio (IOCP and io_uring) as a later experiment behind a transport trait. Do not plan on io_uring, since container seccomp profiles block it by default.
- Backpressure: bound each connection's egress queue by bytes, not packet count. Use a Valence-style byte_channel or an atomic pending-bytes counter plus Notify, with a configurable soft limit (stop sending low-priority traffic such as chunks) and a hard limit (disconnect). Pumpkin's hard limit is 64 MiB. Keep a separate high-priority lane for keepalive and teleport.
- Keep CPU work out of tokio workers: compress and serialize chunks in the tick's parallel phase (rayon) or on a dedicated compression pool, not spawn_blocking. Encryption can stay in the writer task but should be chunked into slices of 64 KiB or less so each step stays within about 1 ms.
- Compression: put the backend behind a trait. Default to libdeflater (level configurable, default 1-4), with flate2+zlib-rs as a pure-Rust fallback feature. Never use flate2's default miniz_oxide backend. Reuse compressor and decompressor state per connection or per thread. Inflate into an exact-size buffer using the packet's Data Length header.
- Cache each chunk's serialized, compressed, framed packet (invalidated on any change, as Valence's cached_init_packets does). Build broadcast packets once per chunk or region per tick and memcpy them to viewers (Valence Messages with a BVH, or Hyperion's BroadcastLocal). Encryption remains per connection.
- Encryption: start with aes+cfb8, but put CFB8 behind an internal interface so batched decryption (measured about 6x) and multi-buffer encryption across connections on one worker (measured 3-4x) can be added later. Document that deployments behind Velocity or a similar proxy should run the backend unencrypted (offline mode plus forwarding).
- Packet codec: derive macros (Encode/Decode plus a Packet attribute carrying the ID, state and side). Packet IDs, registries, block states and data components are generated from extracted JSON and committed to the repo (Pumpkin's approach, no build.rs). Decoded packets own their payloads through bytes::Bytes or Utf8Bytes instead of borrowing with lifetimes, because events outlive handlers in ECS or queued designs. Budget hand-written work for ItemStack data components and entity metadata (Hyperion estimates 15-20k lines).
- Target one protocol version first (the latest release, 26.3 = protocol 777 per minecraft.wiki; verify). Leave multi-version support to a ViaVersion-style proxy rather than per-version branches in every packet writer, which is Pumpkin's cost.
- Game-state architecture: avoid depending on flecs-rust (safety and maturity problems; Hyperion churned twice). Use bevy_ecs 0.19 standalone, or a custom structure-of-arrays layout for hot data (positions, velocities, AABBs), with a uniform chunk-section grid as the spatial index. If using bevy_ecs, benchmark executor overhead and consider the single-threaded executor within each region.
- Parallelism: prefer region-sharded ticking (Folia-style merge-radius regions, or a checkerboard/graph-coloured region grid) in which each region runs single-threaded logic in parallel with the others. Cross-region interactions go through message queues applied at tick boundaries. Size the tokio, rayon and (if used) bevy_tasks pools explicitly so their total thread count does not exceed physical cores.
- Memory: set `#[global_allocator]` to mimalloc on every target (measured 2.7-4.3x faster than the Windows heap). Consider tikv-jemallocator only on Linux, and only after profiling. Use per-tick bumpalo arenas for scratch data. Block sections: Single / Indirect(u8 or nibble indices plus refcounted palette) / Direct(u16), bit-packing only at serialization, with a dirty flag per section to invalidate cached packets.
- SIMD: stable std::arch with runtime feature detection (safe since Rust 1.87), or the `wide`/`pulp` crates; do not depend on nightly std::simd. Avoid pdep/pext unless dispatch confirms fast BMI2, since Zen1/Zen2 are microcoded.
- Lighting: implement a Starlight-style directional BFS with nibble arrays and skylight bitsets rather than porting vanilla's engine.
- Worldgen: generate the noise router from extracted JSON into a flattened, range-annotated node array (an interpreter) first, then specialize hot routers via codegen or generics. Batch evaluation per 4x8x4 interpolation cell to vectorize, and gate every optimization on vanilla parity fingerprint tests. Parallelize chunk generation through a status DAG with neighbor-dependency tracking (Pumpkin's chunk_system).
- Storage: read and write Anvil (zlib, plus LZ4 type 4) through a pluggable ChunkStorage trait. Do region I/O on a small dedicated blocking pool using positional reads and writes plus an LRU of open region handles. Offer an optional zstd whole-region format (Linear-like) for about 36-48% smaller files. Use a pure-Rust or cc-built codec (ruzstd, lz4_flex, zstd via cc), never a CMake-built C library, so Windows builds keep working.
- Observability from day one: tracing spans for each tick phase, a tracing-tracy layer behind a cargo feature, a `profiling` cargo profile (release plus debug info) for samply on Windows ETW and Linux perf, tokio-console behind a tokio_unstable feature, and metrics+Prometheus for TPS, MSPT, bytes out, queue depths and compression/encryption time.
- Testing: codec round-trip property tests plus cargo-fuzz targets per state decoder (needs nightly; runs on Windows). Add deterministic tick tests with a seeded RNG and a fixed system order, and Hyperion-style differential tests against recorded vanilla traces. For load tests, use a separate workspace with azalea pinned to the server's protocol and a lightweight custom bot (in the style of rust-mc-bot) for 1k-10k connections.

## Open questions
- Is wire-format chunk data as compressible as the NBT I measured? The benchmark used region-file NBT, so real ChunkData packets from a 26.x server should be captured (e.g. with Valence's packet_inspector or azalea) and re-benchmarked.
- How much faster can multi-buffer CFB8 encryption get with u128 shift registers and VAES/AVX-512 (Zen4+, Ice Lake+), and is it worth the complexity if deployments sit behind Velocity (unencrypted backend)?
- What is bevy_ecs 0.19's MultiThreadedExecutor overhead per system on a realistic Minecraft schedule of 100-300 systems? The only hard numbers found are from bevy 0.12 in 2023-2024.
- Does Velocity pass backend-compressed packets through without re-compressing, and should the backend disable compression (threshold -1) when behind Velocity? Not verified in official docs.
- How does zlib-ng compare to zlib-rs and libdeflate on this real chunk corpus? zlib-ng could not be built on Windows here because of MSBuild's 260-character path limit; retest on Linux.
- How does Pumpkin's chunk generation throughput (chunks/s, from its chunk_gen and chunk_gen_concurrent benches) compare with vanilla or C2ME on the same seed? No published numbers were found.
- What scale does each region-sharding choice favor: Folia-style merging regions, a fixed checkerboard grid, or Hyperion's single-world ECS with proxy fan-out, for the expected load (hundreds vs thousands of players, spread out vs clustered)?
- Is the 26.3 protocol (777) final, or still in snapshots? The local launcher shows 26.3 snapshots while minecraft.wiki lists 26.3 as a release. Needs confirmation before pinning a target version.
- Can a vectorized vanilla Perlin/ImprovedNoise implementation (4 or 8 lanes, f64) stay bit-exact with vanilla worldgen? It has to be proven with parity tests before relying on SIMD worldgen.

It should add a first-class proxy mode with no backend compression or encryption, and it should weigh bevy_ecs against a non-ECS core more evenly.

- [confirmed] Velocity's natives use libdeflate for compression and OpenSSL for encryption on Linux. Open question: whether Velocity re-compresses backend traffic.
  -> The natives README confirms libdeflate, OpenSSL 1.1 and 3.x on Linux, and CommonCrypto on macOS. It lists no Windows build. The open question can be answered from source. MinecraftConnection.setCompressionThreshold installs a MinecraftCompressDecoder and encoder on each connection, including the backend connection, and removes both only when the threshold is -1. So packets the backend compresses are decompressed at the proxy and compressed again for the client. Behind Velocity, the backend should set network-compression-threshold=-1, which is the usual community advice. That removes both compression and encryption from the backend's hot path.

- [confirmed] Anvil compression type 4 (LZ4) was added in 24w04a and custom type 127 in 24w05a, with 4 KiB sectors and .mcc files for chunks over 1020 KiB.

## Omissions
- Proxy mode changes the CPU budget. Velocity decompresses backend packets and compresses them again for the client (MinecraftConnection installs a compress decoder on the backend link). Its modern forwarding runs the backend in offline mode, so the backend link is also unencrypted. The core therefore needs a first-class 'behind proxy' mode with threshold -1 and no encryption. In that mode the chunk-packet cache should hold framed, uncompressed packets. The CFB8 multi-buffer and compression work then matters only for direct-connect deployments.
- flate2 pitfall: with the miniz_oxide or zlib-rs backend, compress_vec and decompress_vec zero-fill the Vec's entire spare capacity on every call. This skewed the report's own inflate benchmark, and Pumpkin's reused compression_scratch hits it on every packet. Compress and decompress into slices sized to the data (the wire Data Length gives the exact size), use libdeflater, or bound the scratch capacity.
- FerrumC is being rewritten from scratch (the rework/v2-skeleton branch, 'merge into master soon'). The rewrite has no bevy_ecs (it uses slotmap), uses redb instead of LMDB, supports exactly one version (1.21.8, protocol 772), has fuzz crates for codec, nbt and net, and adds dynamic Rust plugins through libloading. Two of the three active full servers are now non-ECS, which weakens the case for bevy_ecs as the default.
- Hyperion's 26.2 play support is only weeks old (the 763→776 move landed 2026-07-27), and it runs on a patched personal fork of Flecs-Rust. Its architecture is sound as an idea, but it is not yet a proven 26.x implementation, and its README benchmark predates both the protocol and the ECS changes.
- bevy 0.20.0-rc.1 was published 2026-09-15. A project that starts on bevy_ecs 0.19 now faces a breaking upgrade within weeks, and Bevy releases break the API roughly every 3-4 months. If bevy is chosen, isolate it behind a thin layer.
- Tooling for extracting data has changed. Mojang stopped publishing mappings after 1.21.11, Yarn ended, and Fabric intermediary is a placeholder for unobfuscated versions. The vanilla data generator (`java -DbundlerMainClass=net.minecraft.data.Main -jar server.jar --all`) produces packet IDs, registries and block reports without any mod, and decompiling the unobfuscated jar yields real names. This affects whether to depend on a Fabric extractor mod (Pumpkin's approach) or on the vanilla jar alone (Hyperion's approach).
- Known packs in the configuration phase: when the client reports the vanilla 'core' pack, the server can send registry data as names only, with no NBT payloads (Hyperion ships 397 elements across 29 registries this way). That removes a large amount of hand-written registry serialization from the minimum viable server.
- azalea requires nightly Rust (it uses generic_const_exprs, now generic_const_args), and current stable is 1.98.1. Load-test and bot workspaces need their own nightly toolchain, and cargo-fuzz needs nightly too. The server itself can stay on stable.
- The zlib-ng build failure was environment-specific. It can be fixed with a short CARGO_TARGET_DIR or by enabling Windows long paths, so a blanket rule against CMake-built C libraries is stricter than the evidence supports.
