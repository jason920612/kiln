# rust-landscape: survey of Rust Minecraft Java Edition server implementations and reusable Rust libraries as of 2026-09-26

## Context (verified 2026-09-26)
Latest Java release is **26.3** (2026-09-15, protocol **777**). 26.4-snapshot-1 is out. Mojang switched to year-based version numbers: 1.21.11 (2025-12-09, protocol 774), then 26.1 (775, 2026-03-24), 26.2 (776, 2026-06-16), 26.3 (777). **26.1 was the first unobfuscated release.** Mojang stopped publishing mappings and Yarn ended. Decompiled server jars now have real names, so vanilla source is directly readable, and projects port from it (Pumpkin, SteelMC, Hyperion). The vanilla data generator (`--all`) still gives only packet ids and registries, not field layouts. PrismarineJS minecraft-data ships full protocol data only up to 26.1.

## Key lessons
1. **Async game logic was a mistake.** In Aug 2026 Pumpkin ran an "async to sync" refactor in 5 commits touching about 900 files (roughly +50k/−56k lines). Its rules now: game logic runs synchronously inside the tick, Tokio only does I/O, rayon does CPU work, and no lock is held across `.await`. Pumpkin issues on record: CPU work clogging Tokio when rayon was removed (#892), rayon workers panicking with "no Tokio reactor" (#2291), and chunks that could not unload because stray `Arc<Chunk>` references kept them alive (#2040).
2. **ECS churn is expensive.** Hyperion went evenio → flecs (2024-10) → bevy (2025-07) → back to flecs (2026-07). The flecs C side hits asserts under multithreading, and flecs 4.1 forbids creating entities inside multithreaded systems, which forced Hyperion's play-packet decode onto a single thread. Valence's rewrite to evenio died when its lead left; the complaints were that bevy's once-per-frame systems lose cross-type packet order and that build-script registry codegen is too slow. FerrumC dropped bevy for actor shards because it needs shard ownership and deterministic order, and "Minecraft's workload is spatial".
3. **Vanilla parity needs tooling, not memory.** Pumpkin and SteelMC compare against dumps from a vanilla server (Extractor `ChunkDumpTests`, `proto_chunk_test`) and reviewers read the decompiled source. SteelMC reached block-for-block worldgen by removing vanilla's own thread nondeterminism (per-chunk biome cache, fixed feature order). Pumpkin's remaining mismatches come from computing some density-function bounds in f32 where vanilla uses double.
4. **Where the performance comes from:** SteelMC compiles density functions into Rust at build time (with common-subexpression elimination, bounds-based branch elision and SIMD) and schedules chunks as a stage pyramid in epochs. Hyperion offloads broadcast to horizontally scaled proxies (BVH, n² fan-out moved off the game server). Valence writes each packet once into a per-chunk message buffer. MCHPRS compiles redstone into a graph.
5. **Pin one protocol version.** Pumpkin moved multi-version support out to a plugin; FerrumC, SteelMC and Valence each support a single version.

## Reusable vs write-ourselves
Reusable: simdnbt (MIT; 4.3 GiB/s borrowed read), Pumpkin Extractor (MIT) or SteelExtractor (CC0), azalea crates (MIT, but the workspace needs nightly) for test bots and reference code, redb or heed or fjall, zlib-rs or libdeflater, lz4_flex, RustCrypto `aes`/`cfb8`/`rsa`, glam, bevy_ecs (if we use an ECS at all), rust-mc-bot / BotMark / Mineflayer for load tests. Pumpkin (GPL-3.0) and SteelMC (AGPL-3.0) are study material only; copying their code imposes their license. Valence crates on crates.io are frozen at 2023 releases. Must write: the tick scheduler and threading model, world/chunk storage, the worldgen compiler, the lighting engine, entity AI, redstone, and ItemStack's data components (Hyperion found 111 component types; only 200/256 packets can be recovered mechanically).

## Design implications
- Make gameplay simulation synchronous and ordered from day one: no async fn in block, item, entity or AI behaviour. Pumpkin spent about 50k lines of churn in Aug 2026 undoing async game logic. Keep Tokio (or a completion-based runtime) strictly for sockets and disk, and run chunk generation, lighting and serialisation on a separate CPU pool connected by bounded channels.
- Choose the parallelism unit on purpose. Options seen: per-world tick threads (SteelMC), actor shards of 8×8 chunks with ownership and cross-shard messages applied at tick boundaries (FerrumC v2, Folia-like), ECS system/entity parallelism (Hyperion), and rayon par_iter over Arc'd entities with atomics (Pumpkin, which gives non-deterministic order and AtomicCell global-lock fallbacks). For vanilla parity plus scaling, the ownership-based region/shard model is the most defensible. Vanilla's global tick order must be preserved inside each region.
- Do not build the core on a third-party ECS unless its execution model matches the need for deterministic order. Hyperion changed ECS three times, Valence's rewrite stalled, and FerrumC abandoned Bevy. If ECS-like layout is wanted, copy FerrumC's pattern: SlotMap entity ids plus per-component Vecs owned by the region, with systems as plain functions called in explicit order.
- Treat worldgen as a compiler problem. Copy SteelMC: parse the vanilla datapack density-function graph at build time, apply common-subexpression elimination and bounds-based branch elision, and emit native Rust, with SIMD where possible. Schedule chunk stages as a dependency pyramid processed stage by stage in parallel. Use f64 exactly where vanilla does; f32 shortcuts break parity. If runtime datapack worldgen matters, keep an interpreter fallback next to the compiled fast path.
- Build a vanilla-parity harness before building features. Use an extractor mod (fork the MIT Pumpkin Extractor or the CC0 SteelExtractor) to dump registries, density-function test vectors, and chunk and biome dumps from the real server. Compare generated chunks block for block, and patch vanilla's own nondeterminism (per-chunk biome cache, fixed feature order) in the reference dumps, as SteelMC did.
- Target one protocol version, 26.3 (777), now; 26.4 is already in snapshots. Generate packet ids and registries from data. For layouts, use derive macros on hand-checked structs, optionally backed by Hyperion-style extraction from the decompiled unobfuscated jar (about 200 of 256 packets mechanical). Budget substantial hand work for ItemStack and its 111 data component types, entity metadata, and the chunk and light packets. Keep golden-byte tests against vanilla captures, because round-trip tests hide symmetric bugs.
- Encode outbound packets once, not once per viewer. Copy Valence's per-chunk message buffer (byte ranges plus a BVH, sorted and deduplicated at tick end) or Hyperion's thread-local BytesMut egress. For very large player counts, keep a later option for Hyperion-style broadcast proxies that absorb the n² fan-out. Give each connection bounded, prioritised outbound queues that disconnect on overflow (FerrumC v2).
- Never run catch-up ticks. Clamp the tick schedule to 'now' (Pumpkin clamps; FerrumC v2 forbids catch-up by policy). Record per-phase tick timings from the start (Pumpkin logs chunk, player and entity phase timings).
- Hold chunks by ownership, not shared Arcs. Pumpkin's Arc<Chunk> leaks blocked chunk unloads. Prefer region-owned chunk maps with handles or generation-checked ids, and load and save through a dedicated storage worker using batched transactions.
- Storage: keep Anvil read/write for compatibility, and put the native format behind a trait. Candidates: a SteelMC-style sector region format with power-of-2 bit packing (no cross-u64 spans) and zstd/LZ4, or an embedded KV store (redb 4.x pure Rust, or heed/LMDB for mmap zero-copy reads). Benchmark chunk load throughput under player movement while dirty chunks are flushed, as FerrumC planned but never did.
- In-memory chunk sections: Pumpkin uses byte-indexed or dense u16 cubes (fast get/set, more memory). Vanilla and SteelMC on disk use bit-packing. Measure both; a byte-index palette with at most 256 entries and a fallback to direct storage is a reasonable default for tick-time reads.
- Plugins: do not publish a plugin API early (SteelMC's stance). When it comes, expose capabilities and intents (FerrumC v2's WorldView, CommandSink and intents), not raw internals or ECS queries. Offer WASM Component Model plugins (Pumpkin shows wasmtime + WIT is viable across languages) plus optional trusted native plugins behind a C ABI. Expect re-entrancy trouble (Pumpkin #2056, #3593).
- Reuse rather than write: simdnbt (NBT), zlib-rs or libdeflater (zlib), lz4_flex, the RustCrypto aes/cfb8/rsa crates, glam, redb or heed, azalea for test bots (it needs nightly), and BotMark or rust-mc-bot for load. Write ourselves: the scheduler, region ownership, the worldgen compiler, lighting (ScalableLux-style parallel engine), redstone (consider MCHPRS-style graph compilation as an optional fast path, keeping a vanilla-exact path as the default), entity AI, and inventory/menu semantics.
- Do not copy code from Pumpkin (GPL-3.0) or SteelMC (AGPL-3.0) unless we accept their license. Use them as design and parity references, and reuse only permissively licensed pieces (Pumpkin's plugin crates are MIT/Apache, the Extractor is MIT, SteelExtractor is CC0, azalea and simdnbt are MIT).
- Define performance targets and a benchmark method now, because every project lacks comparable loaded-MSPT numbers. Pumpkin only publishes idle RAM; SteelMC only chunk-gen throughput; Hyperion's tick time excludes proxy work. Measure: MSPT at N bots with fixed seed, view distance and movement pattern; chunk-gen chunks/s and chunks per CPU-second against vanilla; RSS per loaded chunk and per player.

## Open questions
- Pumpkin's actual MSPT and memory at 500–1,000 moving bots after the Aug 2026 async-to-sync refactor. The 1.0 roadmap ticks the '1000+ players' stress test, but no numbers are published. The docs.pumpkinmc.org/about/benchmarks page returned 404.
- SteelMC's gameplay tick performance with players and entities. Only worldgen throughput is published, and the entity-spawn stage is disabled.
- How SteelMC admits packets 'between ticks' without data races: the exact synchronisation at tick start and how gameplay packets are ordered relative to the tick. The code (steel-core/src/server/packet_processor.rs, run_loop.rs) was not reviewed in depth.
- Whether FerrumC v2 will merge to master and ship multi-shard runtime and terrain. Its STATUS.md shows 85 commits unpushed locally as of 2026-06-29, and the last public push was 2026-08-14.
- Whether Hyperion ever held its 10k-player PvP record event, and with what real-world tick times (unverified). Also its current MC target after the 26.2 codegen work.
- Real memory and CPU cost of the byte-indexed palette (Pumpkin) versus bit-packed in-memory sections (vanilla) for tick-heavy workloads. No Rust project publishes this comparison.
- Whether a regionized/sharded tick model can keep vanilla-exact cross-region semantics (redstone, entity interactions near shard borders, global block-event order) that parity tests would detect. No Rust project has proven this yet. Folia (Java) is the precedent but was not researched here.
- How to support datapack-defined worldgen if density functions are compiled at build time (SteelMC chose not to). Options: hybrid interpreter plus JIT (Cranelift), or rebuilding on datapack change.
- Viability of io_uring or completion-based runtimes (compio) instead of Tokio for networking at high player counts. Valence planned compio and Graphite used io_uring, but neither published numbers.
- The exact list of Pumpkin redstone components currently broken or incomplete after the 0.2.0 piston PRs. The third-party article from 2026-08-29 may be stale.

## Omissions
- No test client can speak 26.3 today. rust-mc-bot is on 1.21.8, BotMark and azalea on 26.2, Mineflayer and minecraft-data on 26.1. Targeting 26.3 means either a ViaProxy hop in every test (ViaVersion 5.12.0 has had 26.3 since 2026-09-18) or building our own bot client. Targeting 26.2 (776) instead gives us native azalea and BotMark bots plus SteelMC and Temper as same-version references. This choice should be made on purpose.
- Nightly vs stable Rust changes which libraries we can reuse. simdnbt 0.10.0, azalea, SteelMC (nightly-2026-08-21) and Hyperion (nightly-2026-07-27) all need nightly. Pumpkin and Temper are on stable, and Temper needed a de-nightlied simdnbt fork to get there.
- A lot of this landscape is AI-generated, and the 'lessons' should be weighted accordingly. FerrumC v2's STATUS.md describes 'autonomous' 32-lane agent batches and Codex merges, and ADR-0002 cites 'AI agent complexity'. Hyperion's recent PRs (#955, #956) are Claude Code-generated. Pumpkin rejected an entire batch of about 20 AI-labelled worldgen parity PRs. Pumpkin's and SteelMC's contributor policies restrict autonomous AI PRs.
- Anvil (.mca) compatibility is thin. SteelMC has no Anvil support, Valence's is read-only, FerrumC v2 only has an import reader, and the only full read/write is Pumpkin's (GPL-3.0). A permissively licensed server needs its own Anvil read/write, or fastanvil after checking its license and whether it supports 26.x.
- The SteelMC speed claim has no optimised Java baseline: no C2ME, ScalableLux, Lithium or Paper Moonrise. The Java precedents that shaped SteelMC, and the regionized-tick precedent (Folia), are not surveyed. A fair target should be set against C2ME and Paper/Folia, not stock Fabric.
- bevy 0.20.0-rc.1 was published 2026-09-15, so choosing bevy_ecs 0.19.1 means an imminent migration. Temper and azalea are on 0.19.
- Pumpkin 0.2.0 added telemetry. Worth knowing if Pumpkin is used as a comparison or deployment baseline.
- MCHPRS Redpiler compiles only a subset of components (repeater, comparator, torch, stone button, lamp, lever, stone pressure plate, wire), with no pistons or observers. As an 'optional fast path' it covers only pure-logic circuits, and the claim that it drops quasi-connectivity is unverified.
- ViaVersion's same-week 26.3 support backs the single-version-core-plus-proxy strategy. We should still check that ViaProxy/Velocity handle our chosen version before relying on it for older clients.
