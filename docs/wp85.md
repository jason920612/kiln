# wp85:worldgen 資料包(自訂群系、噪音設定、地物、結構、維度類型、維度,與 vanilla 跑同一批資料包一樣)

分支 `wp85-worldgen-packs`(從 main `82165ceb` 開出,只推到 `vm`)。做法承襲 wp72~wp83:**兩邊同一個世界**(同種子、同資料包、同維度設定)、**能直接問 vanilla 的就問 vanilla**(`javap`/`tools/jpv.py` 讀位元碼;用 vanilla 的 jar 當函式庫、讓它的 `MinecraftServer` 載入同一批資料包)、每個新行為有「拿掉就失敗」的負向檢查(`tools/wp85/neg85.py`)。所有建置與測試只在 VM(`~/kt wp85-worldgen-packs …`,`CARGO_BUILD_JOBS=3~4`);Kiln 25599、vanilla 25596(harness 25597);Mojang 的資料留在 `work/`,測試資料包(`tools/wp85/packs/`)全是自己寫的小 JSON 與一個自己做的結構模板,沒有複製任何 Mojang 的檔案(連覆寫 vanilla 條目的也是自己寫的最小版)。

## 1. vanilla 怎麼做(`javap` 讀 26.3)

| 環節 | vanilla | 要點 |
|---|---|---|
| 維度從哪來 | `WorldLoader.load`:先載 `WORLD_REGISTRIES`(群系、噪音設定、地物、結構、維度類型…),再載 `DIMENSION_REGISTRIES`(`dimension/*.json` 的 `LevelStem`);`WorldDimensions.bake(registry)`:**資料包的 `LevelStem` 優先,存檔 `world_gen_settings.dat` 的 `dimensions` 補沒有的**;順序是 overworld、the_nether、the_end(`BUILTIN_ORDER`)再來其他 | vanilla 的資料(`data/minecraft`)裡沒有 `dimension/` 檔,三個維度是 `world_preset/normal` 內嵌的;資料包可以覆寫 `minecraft:overworld` 本身 |
| 生成器 | `LevelStem.generator`:`minecraft:noise`(`settings` 是 id 或內嵌物件,`biome_source`:`multi_noise`〔`preset` 指 `multi_noise_biome_source_parameter_list` 的條目,或內嵌 `biomes` 參數表〕、`the_end`、`fixed`、`checkerboard`)、`minecraft:flat`(內嵌 `settings`:`layers`、`biome`、`features`、`lakes`、`structure_overrides`)、`minecraft:debug` | 不透明的 flat 層直接填,不透明以外(水、植物)由 `FillLayerFeature` 在 `TOP_LAYER_MODIFICATION` 補(結果等同直接放) |
| 條目順序 | 每個 registry 的條目依 `Identifier` 排序(**path 先、namespace 後**)註冊;結構在同一步驟(`step`)裡的 `setFeatureSeed(…, j, step)` 編號、結構集試的順序、群系 → 地物排序都跟它走 | 資料包的新條目因此會插在 vanilla 條目中間,不是排在最前或最後 |
| 範本 | `StructureTemplateManager` 依資源管理員(資料包疊在 vanilla 上、後蓋前)找 `data/<ns>/structure/<path>.nbt`;26.3 的調色盤項目是 `{id, properties}`(`{Name, Properties}` 是舊格式,vanilla 載入時讀成空氣),方塊位置是 `ListTag` | 第一版我寫的範本用 `Name` 與 `IntArray` 位置,vanilla 的方塊全是空氣而 Kiln(寬鬆的讀法)放了方塊——兩邊不同的原因,不是 Kiln 的錯,範本改成 26.3 格式 |
| 維度類型 | `DimensionType.DIRECT_CODEC`:`min_y`(16 的倍數)、`height`(16 的倍數、`min_y + height ≤ 2032`)、`logical_height ≤ height`、`coordinate_scale` 1e-5~3e7、`has_skylight`、`has_ceiling`、`has_ender_dragon_fight`、`infiniburn`、`ambient_light`、`monster_spawn_*`、`attributes`(`gameplay/bed_rule`、`fast_lava`、`respawn_anchor_works`、`piglins_zombify`、`can_start_raid`…)、`timelines`、`default_clock` | 時間相關的行為(睡覺跳夜、天空亮度、蜜蜂回巢…)來自 `timelines` 裡的 `minecraft:day` 等,時鐘來自 `default_clock` |
| 傳送門 | `Entity.handlePortal`:下界傳送門 `level.dimension() == NETHER ? OVERWORLD : NETHER`,座標用兩個維度類型的 `coordinate_scale` 比;終界傳送門同理對 `END`;重生/天氣/`canHaveWeather`(有天光、無天花板、不是 End 的 key) | 自訂維度的下界傳送門去下界,從下界回來去的是主世界(不是原來那個維度) |

## 2. Kiln 的做法

| 元件 | 位置 | 做什麼 |
|---|---|---|
| 一疊根目錄 | `kiln_worldgen::Datapack::load_stack(roots)`(`load(root)` 是它的一個根的特例) | vanilla 的資料在底,世界啟用的資料包依載入順序在上;同 id 的檔後蓋前;worldgen 與方塊 tag 依 `TagLoader` 疊加(`replace` 清掉前面的、巢狀、可選);條目依 `Identifier` 順序(`stacked_entries`);結構模板 `TemplateManager::near_stack`(資料包的 `structure/*.nbt` 在 vanilla 的 jar 之前);`reports/biome_parameters` 從最上面有的根找 |
| 維度清單是執行期的 | `kiln_data::levels`(`Level { key, dimension_type, biome }`、`levels()`、`install_levels`、`level_type`、`install_dimension_types`)、`kiln-sim/src/dimensions.rs`(`stems`、`levels`、`install_types`、`dimension_type_from_json`) | 啟動時:存檔的 `dimensions`(NBT → JSON)疊上資料包的 `dimension/*.json`,vanilla 三個永遠在前;每個維度有自己的 `Dim`(存檔目錄 `dimensions/<ns>/<path>`、天氣、睡眠狀態、世界邊界、強制載入、路標、編輯批次…全是依維度數量的 `Vec`);`DimId` 還是索引,`OVERWORLD_ID/NETHER_ID/END_ID` 仍是 0/1/2,`DIMENSIONS` 常數換成 `dim_key/dim_biome/dim_count/dim_type` |
| 維度類型來自 registry | `kiln_data::DimensionType`(新欄位:`bed_can_sleep`、`bed_can_set_spawn`、`bed_error`、`piglins_zombify`、`can_start_raid`、`nether_portal_spawns_piglin`、`timelines`;`xtask/src/codegen.rs` 與生成檔同步)、`dimensions::dimension_type_from_json` | 資料包新增或覆寫的 `dimension_type` 條目解碼成同一個結構(`kiln_data::dimension_type(name)` 先看資料包的);vanilla 的 codec 會擋的(高度不是 16 的倍數、`logical_height` 太大、尺度 0…)Kiln 也擋,擋掉的不會送給客戶端 |
| 依維度類型取代寫死的維度 | 睡覺規則(`sleep.rs` 讀 `bed_rule`)、重生錨(`respawn_anchor_works`)、突襲(`can_start_raid`)、豬布林殭屍化(`piglins_zombify`)、傳送門生豬布林(`nether_portal_spawns_piglin`)、天氣(`has_skylight && !has_ceiling && 不是 End`)、天空亮度/蜜蜂/眼睛花/海龜蛋/苦力怕…(`timelines` 含 `minecraft:day`)、地獄風的生怪高度(`has_ceiling`)、日光感測器(`has_skylight`)、`/time` 的預設時鐘(`default_clock`)、`coordinate_scale`(`/execute in`、`/tp`、傳送門)、海平面(生成器的噪音設定,平坦是 -63) | 傳送門:去哪裡照 vanilla 的規則(自訂維度的下界傳送門去下界);沒改的寫死:`dragon_fight`/`gateway`/終界傳送門只對 `minecraft:the_end` 這個 key、`portals_light` 只對 overworld 與 nether(vanilla 也是看 key)、游蕩商人/貓/村莊/巡邏只在 overworld(vanilla 的 custom spawners 只給 overworld) |
| 生成器(`kiln-worldgen/src/stem.rs`) | `Datapack::parse_stem`、`Stem`、`StemGenerator::{Noise, Flat, Debug}`、`SourceSpec`、`Worldgen::from_stem`、`FlatChunks`、`vanilla_stem`/`stems_of`、`BiomeSource::{Fixed, Checkerboard}`、內嵌的噪音設定(登記成 `inline:<key>`) | 噪音維度走原本的 `Pipeline`(地形、洞穴、地物、結構一樣);平坦維度用 `FlatChunks`(層、單一群系,沒有結構與地物;非不透明層與直接放等價);`debug` 與沒有 vanilla 資料時的噪音維度是空世界 |
| 群系的設定讀資料包 | `SpawnTable::load(roots)`(生怪、`spawn_costs`)、`Climates::load(roots)`(溫度、降水)、`StructureSpawns::load(roots)`(結構的 `spawn_overrides`),`world_state::{worldgen_ids, worldgen_tag, templates, stacked_json}` | `/locate`、`/place`、探險家地圖、tag 補全用的都是疊起來的資料;覆寫 vanilla 群系時生怪與氣候都跟著變,不只是客戶端的顏色 |
| 條目驗證 | `kiln-sim/src/registry_schema.rs` + `registry_data::load` | 對 14 個 registry(畫、傷害類型、歌曲、樂器、鑲飾圖案與材料、橫幅圖案、裝飾陶罐圖案、各種變體、聊天類型、對話框、群系)照 vanilla 的 codec 檢查欄位型別、範圍與列舉值;**規則不是我猜的**:`tools/wp85/packs/kiln85_bad`(50 多個故意寫壞或邊界的條目)讓 vanilla 自己載一次,它的錯誤清單就是答案(`schema_accepted.txt`),`registry_data` 的測試要 Kiln 留下與擋掉的完全一樣 |
| 鋤、斧、鏟 | `block_transformer.rs` | 沒有資料包覆寫時讀 vanilla 的 `data/minecraft/block_transformer/{hoe,axe,shovel}.json`(讀不懂的才退回 `tools.rs` 內建規則) |

## 5. 驗證過程中找到並修掉的(不在題目清單上的)

- **同一 registry 的條目順序**:`Datapack` 用 `namespace:path` 字串排序,vanilla 是 path 先 namespace 後;一個資料包的新結構會排在所有 vanilla 結構前面,結構的 `setFeatureSeed` 編號、結構集試的順序都和 vanilla 不同。修成 `Identifier` 順序,單元測試鎖住。
- **`SimLevel` 到處有的 3 個維度**:`world_state` 的邊界/強制載入/票、`edits` 的批次、`sleep_status`、`waypoints`、`level_weather` 全是長度 3 的陣列,第四個維度一上線就 panic;全改成依維度數量的 `Vec`。
- **範本格式**:見 §1。Kiln 對 `Name`/`IntArray` 位置的寬鬆讀法比 vanilla 26.3 寬(vanilla 會讀成空氣);沒改(舊世界的範本有 `Name`,vanilla 靠資料修復器轉換)。
- **vanilla 世界不是決定性的**:同種子的兩個 vanilla 伺服器世界,沙漠區 256 chunk 有 22,601 個方塊不同(礦脈、樹、玄武岩柱跨 chunk 的順序);所以真正的逐方塊比對用正規順序的 harness,伺服器世界只用在決定性的案例(平坦維度:64 chunk、0 方塊不同)。
- **平坦維度的草方塊**:草方塊上蓋水層時 vanilla 的隨機刻會把草變泥土,和生成無關;測試的層改成石頭下夾水。
