# wp83:資料包的 registry 與 tag(伺服器跑資料包,行為要和 vanilla 跑同一批資料包一樣)

分支 `wp83-datapacks`(從 main `ba0f822c` 開出,只推到 `vm`)。做法承襲 wp72~wp81:**兩邊同一個世界**(同種子、同方塊、同時間、同 gamerule、同視野與模擬距離)、
**能直接問 vanilla 的就問 vanilla**(`javap`/`tools/jpv.py` 讀位元碼,用 vanilla 的 jar 當函式庫跑它自己的 `WorldLoader`)、每個修正用「關掉它測試必須失敗」的負向檢查(`tools/wp83/neg83.sh`)。
所有建置與測試只在 VM(`~/kt wp83-datapacks …`,`CARGO_BUILD_JOBS=3~4`);Kiln 25589、vanilla 25595;Mojang 的資料留在 `work/`,測試資料包(`tools/wp83/packs/`)全是自己寫的小 JSON,
沒有複製任何 Mojang 的檔案(連覆寫 vanilla 條目的也是自己寫的)。附魔(項目 4 的附魔部分與項目 5)與 loot 呼叫(項目 6)由兩個獨立的 Claude 工作階段在分支 `wp83-enchant`、`wp83-loot` 做完後合併,各自的細節在 `docs/wp83-enchant.md`、`docs/wp83-loot.md`,本檔摘要。

## 1. vanilla 怎麼做(`javap` 讀 26.3)

| 環節 | vanilla | 要點 |
|---|---|---|
| 條目順序 = 網路 id | `RegistryDataLoader.load` → `ResourceManagerRegistryLoadTask.load`:`listMatchingResources`、**以 `Identifier` 排序**後 `registerElements`;`Identifier.compareTo` 先比 **path** 再比 namespace | 一個資料包的新條目會把排在它後面的所有條目 id 往後推(生物群系調色盤、傷害類型、變體、附魔…所有按 id 送的東西都會變) |
| 載入時機 | `WorldLoader.load`(世界載入時一次);`/reload` 只重載 `ReloadableServerResources`(tag、配方、loot、function…),**不動這些 registry** | 新增的條目要重啟才出現 |
| 送給客戶端 | `SynchronizeRegistriesTask`:先送 `SelectKnownPacks`(伺服器的 pack 清單 = `minecraft:core`…),客戶端回覆後 `RegistrySynchronization.packRegistries`:**來自客戶端認得的 pack 的條目不帶資料**(`knownPackInfo`),其餘(資料包新增的、覆寫 vanilla 的)帶 NBT;資料用各 registry 的 **network codec**(例如變體不送 `spawn_conditions`、生物群系不送特徵與生怪) | 客戶端回的清單和伺服器要的不一樣時,全部帶資料 |
| tag | `TagLoader.load/build`:依 pack 順序疊加,`replace` 清空之前的,巢狀 tag 就地展開、去重、`required:false` 缺的略過,必要條目缺或循環就**這個 tag 不載入**(log 錯誤,其他照載);`TagNetworkSerialization` 送 id 清單(順序 = tag 展開順序) | 設定階段送一次,`PlayerList.reloadResources` 在 `/reload` 後對所有玩家再送 |

## 2. Kiln 的做法

| 元件 | 位置 | 做什麼 |
|---|---|---|
| `kiln_data::live` | `crates/kiln-data/src/live.rs` | 行程共用的「現在的」registry 與 tag 表(`synced()`、`tags()`、`synced_id`、`tag`、`entry_data`、`from_vanilla_id`…)。沒有資料包時就是 `registries::SYNCHRONIZED/TAGS` 的靜態表;有資料包時模擬端裝上新表(洩漏成 `&'static`,內容相同的不重洩;`generation()`、`registry_generation()`)。`Cached<T>`:依代數重建的衍生表,讀取只是一次載入加比較 |
| 條目載入 | `crates/kiln-sim/src/registry_data.rs` | 每個同步 registry:vanilla 的條目名 ∪ 各啟用資料包(vanilla 以外,依載入順序,後蓋前)的 `data/<ns>/<registry>/**.json`,依 `Identifier` 順序排;JSON 轉 NBT(整數 → int、其他數 → double、布林 → byte、混合清單包 `{"":v}`,與客戶端 codec 讀法一致);network codec 去掉的欄位(變體的 `spawn_conditions`、生物群系的 `features/carvers/spawners/…`)去掉;缺少 codec 必要欄位的條目略過並記錄(vanilla 會整個停止載入) |
| 啟動順序 | `Sim::new`(`crates/kiln-sim/src/lib.rs`)、`datapacks.rs` | **最先**打開世界存檔、決定啟用的資料包、裝上 registry,然後才建生成器、區塊來源、玩家封包(生物群系 id 等都用現在的編號);之後 `init_packs`:**先**載 tag(`install_tags`)**再**載配方、loot、function(它們載入時解析 tag);`/reload` 同序 |
| tag 載入 | `crates/kiln-loot/src/tags.rs`(`Tags::load_sources`)、`crates/kiln-sim/src/tags.rs` | 一個載入器:`TagSource::{Dir, Builtin}`(沒有 vanilla 檔案時用內建的),逐 tag 容錯(缺必要條目、循環就不載入並記錄,其他照載),結果同時給 loot 解析、遊戲邏輯(`live`)與網路 |
| 送給客戶端 | `kiln-link` `DataSync.registry_packets`、`kiln-net` `configure` | 登入的 `Registry Data`:沒有資料包時是原本的「只有名字」封包(**位元組不變**);有資料包時是帶條目資料的封包(條目資料只有伺服器端那些客戶端認不得的) |
| 讀 tag / registry 的地方 | 全部約 75 處(`kiln-blocks`、`kiln-inventory`、`kiln-command`、`kiln-entity`、`kiln-sim`、`kiln-loot`、`kiln-item`、`kiln-storage`、`kiln-worldgen` 的方塊 tag…) | 都讀 `live`;帶快取的(每方塊狀態旗標表、`Registry::id` 索引、物品預設元件、原生存檔的生物群系表、執行緒區域快取…)改成 `Cached`/代數檢查 |
| 物品預設元件 | `kiln-item/src/defaults.rs`、`component/mod.rs` `renumber` | 預設元件表存的是 vanilla 的 id;資料包新增條目後(例如歌曲 `kiln83:tune` 排在 `wait` 前)音樂唱片的歌、錠的鑲飾材料會錯位。改成讀進來時換成現在的編號(歌曲、鑲飾圖案與材料、樂器、畫、旗幟圖案) |

## 5. 項目 7:worldgen 資料包(自訂群系、噪音設定、地物、結構、維度類型、維度)——不做,現況與要做什麼

**Kiln 現在讀什麼**

- `kiln_worldgen::Datapack::load(root)`:**只讀一個目錄**(`KILN_DATAPACK`,vanilla 的 `generated`)底下所有 namespace 的 `worldgen/*`(`noise`、`density_function`、`noise_settings`、`material_rule/condition`、`biome`、`carver`、`multi_noise_biome_source_parameter_list`、`feature`、`placed_feature`、`block_state_provider`、結構相關)、`dimension_type` 與 tag 檔。世界的資料包完全沒進去;方塊 tag(`vtags.rs`、heightmap 旗標)現在改讀 `live`,所以資料包改 `#blocks_motion_in_heightmap`、`#features_cannot_replace` 這類 tag 會影響新生成的區塊,但 `Datapack` 自己載的 JSON tag 還是 vanilla 的。
- 生物群系**名稱與 id** 進了 registry(資料包的群系有 id、會送給客戶端,網路形式去掉 `features`/`spawners` 等,沒做屬性同步過濾),但生成器沒有它的氣候參數,所以不會被放進世界;資料包覆寫 vanilla 群系時,客戶端看得到新的霧/顏色,伺服器的生怪、生成不變。
- 維度:三個固定(`DIMENSIONS`、`kiln_data::dimension_types` 的靜態結構:`min_y`、`height`、`logical_height`、環境光、時鐘…);`level.dat` 的維度設定、傳送門、天氣、`/execute in` 都假設這三個。維度類型條目會送給客戶端,但伺服器模擬用靜態的那份,覆寫 `min_y/height` 會讓兩邊不同步。

**要做什麼**

1. `Datapack::load` 吃一疊根目錄(vanilla 在最底,再加世界啟用的資料包,依序),同 id 後蓋前、worldgen tag 的 `replace` 照 §2 的 tag 載入器;結構模板(`TemplateManager::near`)同樣一疊。
2. 自訂群系:`multi_noise_biome_source_parameter_list` 與 `world_preset` 要由資料包決定哪些群系在哪些氣候點;生成器內部的群系 id 要用 registry 的 id(已經是);群系生怪設定(`SpawnTable`)與群系 tag 的特徵/結構(`has_structure/*`)讀資料包的版本。
3. 自訂噪音設定/密度函數/地物/放置地物/結構/結構集/模板池/處理器清單:表達式編譯器本來就吃 JSON(`graph.add_function`),缺的只有 1 的疊加與 registry 順序;結構的 `StructureSet` 與 `/locate`、`/place` 的名單(`world_state::worldgen_ids`)要改讀疊起來的資料。
4. 自訂維度類型與維度:`kiln_data::dimension_type` 改讀 registry 條目(`min_y`、`height`、`logical_height`、`has_skylight`…),`DIMENSIONS`/`DimId` 常數改成執行期清單(每個維度:`level_stem`、生成器、存檔目錄、天氣/時鐘、傳送門目標、`Respawn`/`Login` 封包的維度類型 id),`level.dat` 的 `dimensions` 讀寫。這是最大的一塊(整個 sim 假設三個維度)。
5. 驗證:用 `tools/ChunkVectors.java` 風格的向量(vanilla 載入同一批資料包生成區塊,逐方塊比較)。

## 6. 附魔(`wp83-enchant`)與 loot(`wp83-loot`)摘要

兩個獨立的 Claude 工作階段(各自的 git 工作樹與 VM 簽出,不開伺服器與客戶端)在 `d14de992`(`kiln_data::live` 已有)之後開出,做完合併回來(沒有衝突)。細節:`docs/wp83-enchant.md`、`docs/wp83-loot.md`。

**附魔(項目 4 的附魔部分、項目 5)**

- **附魔定義只在世界載入時讀一次**(vanilla 的 `RegistryDataLoader` 載入 `enchantment`、`enchantment_provider`、`jukebox_song`、`trade_set`、`villager_trade`;`/reload` 只重讀 tag 與可重載資源):`LootData.world`(`WorldDefs`)留著原文,`/reload` 用它對新 tag 重新解碼。
- **26.3 的每一種附魔效果元件都解碼到欄位**(`Effects.other` 對 vanilla 的附魔是空的):新評估 `tick`、`location_changed`、`hit_block`、`projectile_spawned`、`trident_sound`、`crossbow_charging_sounds`、`prevent_equipment_drop`、`prevent_armor_change`,與效果種類 `replace_block/replace_disk`、`set_block_properties`、`run_function`、`spawn_particles`、`summon_entity`、位置型 `attribute`、`play_sound`、`ignite`、`apply_impulse`、`explode`(`post_attack`)。
- 玩家的 `tick` / `location_changed` 引擎(`kiln-sim/src/enchant_fx.rs`):方塊座標改變、落地、裝備更換、破損時觸發,每個啟用中的效果用「槽位 + 附魔 + 索引」記錄(`enchantment_active_check`);**靈魂疾行者與霜行者不再寫死,就是它們的定義**。
- 投射物:箭與三叉戟的 `hit_block`、玩家/骷髏/掠奪者射出的箭帶著弓執行 `projectile_spawned`;三叉戟的引雷、`trident_sound`、弩的充能音效與充能時間讀定義;弩充能時間與 `trident_spin_attack_strength` 改成所有附魔依序累加(原本只取最高等級那個)。
- 寫死的 vanilla 附魔 id 改讀定義或 tag:絲綢之觸改成 `#prevents_bee_spawns_when_mining`、`#prevents_infested_spawns`、`#prevents_decorated_pot_shattering`;補上「挖冰會融化」(`#prevents_ice_melting`);詛咒改成 `prevent_*` 元件(玩家、生物拾取、剪裝備、死亡掉落);長槍的火焰附加改走 `post_attack`。

## 7. 沒做 / 限制

- **`block_transformer`**(hoe/axe/shovel 的轉換清單,26.3 是資料包 registry):條目有同步給客戶端,但鋤地、去皮、鏟路的規則還是 Kiln 內建的(`tools.rs`);資料包改它不影響遊戲。
- **沒有 vanilla 檔案時**(沒設 `KILN_DATAPACK`):內建的 tag 表是按 id 排序,不是 vanilla 檔案的順序;有資料包時,依 tag 順序挑選的地方(畫的隨機、山羊角、織布機按鈕順序)會和 vanilla 不同。有 `KILN_DATAPACK` 時用檔案順序。
- **客戶端沒有 `minecraft:core`**:Kiln 照舊中斷連線(vanilla 會把所有條目的資料都送過去)。
- **壞條目**:vanilla 會停止載入整個 registry(伺服器起不來);Kiln 略過缺少必要欄位或 JSON 壞掉的條目並記錄(沒有逐 registry 的完整 codec 驗證:欄位型別錯誤的條目仍會送給客戶端,客戶端可能因此斷線)。
- **程式裡寫死 vanilla tag 內容的地方**(以方塊名後綴、名單判斷而不是讀 tag):資料包改該 tag 不影響;沒有逐一盤點。
