# wp64:關掉 wp63 留下的五個小差異(身上的箭與蜂針、旁觀者隱藏、粉雪、蹲下的 tick 順序、瞬間效果)

分支 `wp64-wp63-gaps`(從 main `4dc1cfea` 開出)。做法同 wp63:先用 `javap` 看 26.3 的位元碼,再用真實客戶端(VM 的 Xvfb)+ 旁觀者客戶端的封包間諜,
在 Kiln 與 vanilla 參考伺服器各做同一批動作,逐封包比對(含時間:同一個 tick 的封包不到 20 ms 一組)。

## 工具(相對 wp63 的變動)

| 項目 | 做法 |
| --- | --- |
| 封包間諜 | `ClientCtl` 的 `spylog ts [clear]` 給每個封包到達的時間(ms);新增 `player_info`(動作、遊戲模式、listed)與 `attributes`(是誰的、每個屬性的基底值與修飾)兩種封包的細節 |
| 場景 | `tools/wp58/p64.py arrows|sting|spectator|powder|sneak|instant|all`(`TARGET=V` 對 vanilla);輸出 `~/wp64/<場景>_<K|V>.json`,每個事件是「旁觀者看到的」與「演員自己看到的」兩串依 tick 分組的封包 |
| 腳本 | `wp64_start.sh`(Kiln,埠 25586)、`wp64_vanilla.sh`(vanilla,埠 25592)、`vm_client64.sh`、`vm_observer64.sh`、`build_agent_wp64.sh`;`KILN_CLIENT_PORT` 選要連哪個伺服器 |

踩到的坑:`ssh` 啟動會留下背景程序的腳本要加 `-n` 並把輸出導向 `/dev/null`,否則 ssh 不返回;`/summon` 的 NBT 在 Kiln 有兩處沒讀(見最後),場景要用能走完整路徑的做法(`/damage ... by` 讓蜜蜂生氣);
場景開頭要先 `alive()`(演員死了之後後面的 `tp` 都是白做)。

## 一個共同的根:原版的「先打包、再 tick」

vanilla 一個 tick 的順序是:指令與連線封包(在 tick 與 tick 之間處理)→ `ChunkMap.tick`(誰看得到誰、**每個實體 `sendChanges`:變動的實體資料**)→ 實體 tick。
所以輸入或指令造成的變動在**這個 tick 開頭**就送出,實體自己 tick 造成的變動要到**下一個 tick 開頭**才送。Kiln 原本把實體資料放在 tick 結尾打包,兩者混在一個封包裡。
(蹲下與瞬間效果兩項都是這一個差異的結果。)

修正:`Region::tick` 一開頭先 `update_visibility`、再 `players::broadcast_data`(每位玩家 `pack_dirty` → 觀看者與自己),然後才 tick;結尾的 `update_visibility` 與 `broadcast_movement` 照舊(位置、裝備、事件、屬性)。
配對仍在打包之前,所以新玩家照原版「配對 + 第一次打包各送一次」。

## 1. 身上的箭與蜂針(entity data 12、13)

### vanilla 的行為(位元碼 + 間諜)

- `AbstractArrow.onHitEntity`:`hurtOrSimulate` 成功(沒被擋、沒無敵)、目標是 `LivingEntity`、**穿透等級 ≤ 0** 時 `setArrowCount(getArrowCount() + 1)`(在擊退與藥水效果之前)。
- `Bee.doHurtTarget`:螫傷成功後 `setStingerCount(+1)`,然後才是中毒效果。
- `LivingEntity.tick`(伺服器端):數量 > 0 時,`removeArrowTime <= 0` 就設成 `20 * (30 - 數量)`,然後減 1,減到 ≤ 0 就把數量減 1(蜂針同理,各有各的計時)。計時不是隨機的,只看數量。
- 兩個條目是一般的同步資料:變動時隨該 tick 的打包送給**觀看者和玩家自己**(間諜:`9=17.0 12=1`,螫傷是 `9=18.0 10=[毒的粒子] 13=1` 在同一個封包)。

### Kiln 原本的差異

完全沒有:玩家沒有箭數或蜂針數,射中、螫傷都不會讓任何人看到。

### 修正

`Player` 的 `arrow_count`/`stinger_count` 與兩個計時(`tick_stuck_in_body`,在玩家 tick 的 `base_tick` 之後);`SYNCHED` 加上 id 12、13(17 個欄位);`EntityLevel::stick_in_body`(箭的 `hit_living` 在 `pierce == 0` 且 `hurt` 成功後呼叫、蜜蜂在螫傷成功後呼叫,模擬層替玩家加一);重生歸零。

### 證據

間諜(同一個場景,Kiln 對 vanilla):一支箭 → 觀看者與自己都收到 `9=17.0 12=1`;580 tick(`tick rate 100` 下 5.8 秒)後 `12=0`;蜜蜂被玩家打了之後螫傷 → `9=18.0 10=[…] 13=1`,之後 `13=0`;完全相同。
測試(`player_sync.rs`):`an_arrow_sticks_in_the_body_and_falls_out_in_time`(新增與掉落相隔剛好 580 tick、觀看者與自己同時、創造模式的玩家不會中)、`a_sting_leaves_a_stinger_in_the_body`。

## 2. 旁觀模式的玩家對一般玩家隱藏

### vanilla 的行為

`ServerPlayer.broadcastToPlayer(viewer)`:觀看者是旁觀者 → 看得到(`getCamera() == this`);否則被看的玩家若是旁觀者 → **看不到**。`ChunkMap.TrackedEntity.updatePlayer` 把它放進「看得見」的條件。重新判斷在 `ChunkMap.move(player)`
(玩家下一個移動封包,真客戶端切換模式後一兩個 tick 內就會送);旁觀者的 `PlayerInfoUpdate`(遊戲模式)照常送給所有人,所以分頁清單還在。
間諜(vanilla):創造模式的觀看者在演員變旁觀時收到 `PlayerInfoUpdate` 然後 `RemoveEntities`(不再有實體資料);演員變回生存 → `AddEntity`(配對)。兩個都是旁觀者時彼此看得到;旁觀者變生存 → 看不到另一個旁觀者。

### Kiln 原本的差異

旁觀者只是多了隱形旗標(0=32),一般玩家仍然看得到它的位置與動作。

### 修正

`update_visibility` 的 `sees()` 加上 `v.spectator || !t.spectator`;`/gamemode` 改模式時把 `section` 設成 `None`(視為剛移動,下個 tick 開頭重算誰看得到誰,在打包之前,所以被藏起來的人不會先收到最後一個資料);
`/gamemode` 的 `attributes_dirty` 只有進出創造模式時才設(vanilla:創造的互動距離修飾;旁觀↔生存沒有 `UpdateAttributes`)。

### 證據與已知差異

間諜六個情境(創造看旁觀、旁觀看旁觀、旁觀者變回生存…)的封包集合與順序相同。差異:vanilla 的重新判斷要等客戶端的下一個移動封包(模式變回生存時落地要多一兩個 tick),Kiln 在同一個 tick 開頭做,
所以(a)重新配對的觀看者先收到上一次打包時的旗標(`0=32`),旗標改變緊接在後(`0=0`),vanilla 因為較晚配對直接收到新值;(b)自己看到「另一個旁觀者消失」與「自己的旗標資料」的先後對調。客戶端最後的狀態相同。
測試:`spectators_are_hidden_from_everyone_but_spectators`(分頁清單還在、消失、之後沒有它的資料、變回生存重新出現、兩個旁觀者互看、一個變生存就看不到另一個旁觀者)。

## 3. 粉雪

### vanilla 的行為

`PowderSnowBlock.entityInside`(伺服器端):已知移動的 x 或 z 不為 0 時 `nextBoolean`,為真就 `sendParticles(SNOWFLAKE, x, 方塊y+1, z, 1, 0,0,0, 速度 (randomBetween(-1,1)/12, 0.05, randomBetween(-1,1)/12), ALTERNATIVE)`,
送給 32 格內(`BlockPos.closerToCenterThan`)的所有玩家,**包含玩家自己**。另外 `LivingEntity.baseTick` 每 tick 先 `removeFrost` 再 `tryAddFrost`:凍結中的玩家**每個 tick** 的移動速度屬性都被標成變動(值沒變也送),
`UpdateAttributes` **只列變動的屬性**(間諜:`movement_speed=0.1[powder_snow:-0.05]`),站著不動也是每 tick 一個。

### Kiln 原本的差異

- 抽了 `nextBoolean`,但沒抽兩個 `randomBetween`(之後的亂數序列也錯位),也沒送粒子。
- 凍結的屬性只在值改變時送,而且每次送**全部 30 個**可同步屬性。

### 修正

- `Player::queue_particles`(`pending_particles`)+ 玩家 tick 之後 `players::deliver_particles`:依序抽 `nextBoolean`、兩個 `nextFloat`,把 `snowflake` 封包送給區域裡 32 格內的所有玩家與自己。
- Update Attributes 改成 vanilla 的模型:`attrs_sent`(上次送出的屬性)與目前的差異,只列變動的屬性(第一次與重生後列全部);`tick_freezing` 在凍結修飾存在的每個 tick 標記速度屬性(`frost_marked`)。

### 證據

3 秒走路 + 1 秒(80 tick)在粉雪裡:vanilla 的旁觀者收到 **101** 個 snowflake、Kiln **102** 個(都是約 1.3 個/tick:同一個 tick 內移動封包與伺服器身體各走過方塊一次);站著不動 2 秒:兩邊都是每 tick 一個只列 `movement_speed` 的 `UpdateAttributes`,沒有粒子。
測試:`walking_in_powder_snow_throws_snowflakes`(旁觀者與自己數量相同、80 tick 在 90~140 之間、站著不動為 0)、`a_frozen_player_gets_the_speed_attribute_every_tick`(每 tick 一個屬性、離開粉雪後解凍的最後一個封包、之後安靜)。

## 4. 蹲下:旗標與姿勢在不同的 tick

vanilla:輸入封包先改旗標(entity data 0),姿勢(6)在玩家 tick 結尾的 `updatePlayerPose` 才改,所以先送 `0=2`,50 ms 後(下一個 tick)再送 `6=CROUCHING`;起身同理。
Kiln 原本同一個封包送 `0=2 6=CROUCHING`。有了上面「先打包、再 tick」之後自然對齊:輸入封包 → 這個 tick 開頭打包旗標 → 玩家 tick 改姿勢 → 下個 tick 開頭打包姿勢。
間諜(蹲下、起身、短按三組,觀看者與自己):`+0 ms 0=2`、`+50 ms 6=CROUCHING`、…與 vanilla 逐項相同。測試:`sneaking_sends_the_flag_and_the_pose_a_tick_apart`。

## 5. 瞬間效果(瞬間治療/傷害、噴濺、滯留、箭)

### vanilla 的行為

- `/effect give … instant_health`:指令在 tick 與 tick 之間執行 → `UpdateMobEffect` 立刻送自己 → 下一個 tick 開頭打包 `10=[粒子]` → 該 tick 的實體 tick 套用效果、移除(`RemoveMobEffect`、`SetHealth` 立刻送自己)→ 再下一個 tick 打包 `9=血量 10=[]`。
- 噴濺藥水(`ThrownSplashPotion.onHit`):瞬間藥水 `LevelEvent 2007`(粒子)+ `1054`(破裂聲),其他 `2002` + `1053`;瞬間效果直接套用,**不經過**效果粒子的實體資料。滯留藥水:`2007/1054` 加一個 `area_effect_cloud` 實體。
- 帶藥水的箭:`doPostHurtEffects` 對目標 `addEffect`(持續時間 1/8,至少 1),瞬間效果走和 `/effect give` 一樣的路(下一個 tick 套用)。

### Kiln 原本的差異

- `/effect give` 的瞬間效果在同一個 tick 加上又移除,觀看者**完全看不到**粒子的變動(只有血量)。(根因見最上面。)
- 用 `/summon` 放的噴濺/滯留藥水**丟了 `Item`**(載入時 `item: None`,破裂沒有效果、沒有 level event;存檔也是一樣);帶藥水的箭載入時沒有 `effects`(藥水在世界重載之後也會失效)。

### 修正

`/effect give` 一項由「先打包、再 tick」自然修好;`persist.rs`:噴濺/滯留藥水讀寫 `Item`,箭的 `effects` 從 `item` 的 `potion_contents` 取得(`arrow::effects_of_item`)。

### 證據

間諜:`/effect give instant_health`、`instant_damage`、`instant_health + speed` 的觀看者與自己的封包串與 vanilla 逐項相同(例如觀看者:`10=[粒子]`、下一個 tick `9=… 10=[]`);噴濺藥水的 `2007/1054`、`2002/1053` 與 vanilla 相同。
測試:`an_instant_effect_shows_its_particle_for_a_tick`(粒子一個 tick、移除與血量在下一個)、kiln-entity 的 `a_thrown_potion_keeps_its_item`、`a_loaded_tipped_arrow_has_its_effects`。

## 順手發現(都已修,見上)與沒做的

已修:粉雪的 `nextFloat` 抽取;`UpdateAttributes` 只列變動的屬性(login 與重生的第一個仍列全部);`/gamemode` 的屬性封包只在進出創造時;`/summon` 與存檔的噴濺/滯留藥水與帶藥水的箭。

沒做(都是原本就有的差異,不在這五項之內):
- 生物身上的箭/蜂針(只做了玩家;生物的實體資料條目要永遠送 0 才能歸零,會改到所有生物的配對封包)。
- 蜜蜂等「中立生物」的 `angry_at`(憤怒目標的 UUID)Kiln 不存檔、`/summon` 讀不到(`Anger.target` 是網路 id)。
- 配對時的屬性清單:vanilla 只列「已建立的屬性」(玩家 4 個:`max_health`、`movement_speed` 與兩個互動距離),Kiln 列 30 個。
- 同一個 tick 內生成又死掉的投射物(`/summon` 的噴濺藥水與箭):vanilla 的觀看者先收到 `AddEntity` 再收到 `RemoveEntities`,Kiln 的追蹤在 tick 結尾,所以看不到它。玩家丟出的藥水會飛幾個 tick,不受影響。
- 傷害事件與受傷聲音的順序(vanilla:`DamageEvent`、聲音;Kiln 相反)、傷害事件與 level event 的順序(傷害在 Kiln 是 tick 結尾才送)。
